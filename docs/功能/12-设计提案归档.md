## CLI 执行诊断与故障定位（v2）

日期：2026-11-13。基线：`43265cd`。

原问题是 CLI 卡住或报错后，多数错误被统一归并为“AI 助手生成失败”，stderr 与工具异常只留在服务端日志，且下一轮重试会覆盖按 session 保存的 generation 记录。

本方案分两步演进到 `version: 2` 离线自解释诊断档案：既在界面给出明确、安全的错误分类与建议，又让用户导出的单份 JSON 文件包含**环境版本、进程生命周期、平台 MCP 网关工具记录、终止原因、时间线与证据边界评估**，实现“拿到导出文件即可定界并定位问题”。按用户要求，运行中界面不增加“已运行多久 / 最近多久无进展”等静默提醒，不影响长耗时任务。

### 用户体验

- **具体错误卡片**：失败回复显示原因、稳定错误码、处理建议，并提供“查看详情 / 复制诊断 / 下载诊断”。即使 CLI 零输出失败，对话中仍保留该条失败卡片。
- **零输出停止可追溯**：运行中和成功回复提供按需打开的紧凑“诊断信息”；若因长时间零输出由用户点击“停止”，即使未写入空白聊天消息，页面当前轮次下方仍保留“诊断信息”入口供复制或下载快照。
- **结构化详情视图**：展开详情后可直接查看自动诊断结论（`assessment`）、证据与未知边界、结束原因（`termination`）、运行实例与版本（`environment`）、每次调用的 CLI 版本/端点/进程状态/信号/输出行数与最近输出时间、工具与网关异常（`tools`）以及可折叠的执行时间线（`timeline`）和起始/尾部 stderr。
- **重试不丢现场**：每轮诊断按 `generationId` 独立持久化，重试或继续对话后仍可随时导出历史失败轮次的诊断文件。

### 诊断文件结构（Version 2）

```text
GET /api/assistant/sessions/:id/generations/:generationId/diagnostics
GET /api/assistant/sessions/:id/generations/:generationId/diagnostics?download=1
```

单份导出的 JSON 包含以下核心维度：

1. **环境与实例（`environment` + 调用级配置）**
   - 平台侧：`platformVersion`、`revision`、`modified`、`goVersion`、`os`、`arch`、`instanceId`、`instanceStartedAt`。服务端关键诊断日志统一携带 `diagnostic=<generationId> instance=<instanceId>`，多副本部署可秒级关联后台日志。
   - 调用侧（`attempts[]`）：`cliVersion`、`versionSource`（`managed_inventory` / `package_metadata` / `native_handshake` / `not_reported`）、`binarySource`（`explicit_override` / `managed_inventory` / `discovered`）、只保留 scheme 与 host 的 `endpoint`（不含路径、凭据和查询参数）、`protocol`、`effort`、`nativeSessionId`、`nativeTurnId`。
2. **CLI 进程现场（`attempts[].process`）**
   - 记录 `pid`、`state`（`not_started` / `running` / `start_failed` / `exited` / `unknown_after_interruption`）、`startedAt`、`finishedAt`、`signal`（捕获 SIGKILL/SIGTERM 等系统信号）、`userCpuMs`、`systemCpuMs`、`stdoutLines`、`stderrLines`、`firstStdoutAt`、`lastStdoutAt`、`firstStderrAt`、`lastStderrAt`。
   - 结合时间线的 `cli.initialized`、`model.turn_started`、`model.first_output_delta`、`protocol.result_received`，无需采集正文即可区分“卡在进程启动”、“卡在握手/MCP 列表”、“卡在等待模型首包”或“流式中途断流”。
3. **工具与平台 MCP 网关调用（`tools[]`）**
   - 同时覆盖 CLI 协议上报（`source: "cli"`）与平台会话 MCP 网关实收请求（`source: "gateway"`），自动关联当前 `attemptId`。
   - 记录 `mcp.gateway_initialized`、`mcp.tools_listed`（含工具数与耗时）及 `mcp.upstream_catalog_failed`（外部 TAPD/工蜂 MCP 拉取工具目录失败不再静默吞掉）。
   - 仅在工具失败时提取脱敏错误片段、`statusCode`、`requestId`、`traceId`；成功工具绝不保留输入参数与返回正文。未结束的工具在中断后标记为 `unfinished`，可直接定位卡死在哪个外部工具调用。
4. **抗冲刷首错保留（`firstError`、`firstStderr`、`dropped`）**
   - 保留前 8 行 `firstStderr` 与最近 20 行 `stderr`，防止后续重试冲掉初始报错。
   - 自动解析结构化 stderr 中的 `sampling_error`（如首轮重试时的上游 `401`/`429` 及 `request id`），过滤 Codex 流式顺序无害日志（如 `without active item`），并将泛化占位重连提示（`Reconnecting...`）升级为首个实质性错误事件存入 `firstError`。
   - 所有截断项按类别计入 `dropped`。
5. **终止归因与离线自解释评估（`termination`、`lastCheckpointAt`、`assessment`、`coverage`）**
   - 明确区分 `USER_CANCELLED`（用户主动停止；若停止前已捕获 `firstError` 会主动提示）、`USER_STEER`（中途转向）、`WORKSPACE_LEASE_LOST`（工作区续租失败）、`CHECKPOINT_FAILED`、`GENERATION_SUPERSEDED`、`SERVER_PANIC` 以及 `CHECKPOINT_LOST`（超过 45 秒未收到运行实例心跳，附带 `lastCheckpointAt`）。
   - `domain.AnalyzeAssistantDiagnostics` 纯确定性离线运行，明确分离**已观测证据（`evidence`）**、**受限于边界无法仅凭该文件判定的原因（`unknowns`）**与**下一步排查动作（`nextSteps`）**，绝不捏造根因或伪造分布式 `traceId`。

### 存储与隐私安全边界

- 新增手工迁移脚本 `migrations/029_assistant_diagnostics.sql`（遵循仓库规则，不在启动代码做 seed 或数据回填）。
- 权限校验与会话非正文附件一致：验证登录态与项目/会话访问范围，公开项目会话只读链接仅暴露固定文案摘要，不暴露详细诊断片段。
- 脱敏覆盖用户与平台注入的各类 API Key、Agent CLI Key、Git Token、Refresh Token、Authorization 头、常见密码/密钥键值、PEM 私钥、URL 查询参数/凭证段（含 `/mcp/` 会话令牌路径）、本机绝对路径及 ANSI 控制序列。不采集提示词、思考正文、工具参数、成功工具输出、环境变量或完整 stdout。

## GitHub 登录与仓库授权统一方案

状态：设计建议，尚未修改登录和账号创建逻辑。

### 用户流程

登录页提供「使用 GitHub 继续」作为推荐入口，账号密码作为其他登录方式保留。首次 GitHub 登录时，在部署允许注册的前提下自动建立平台账号；已有绑定的用户直接进入工作台。用户无需单独填写用户名、密码和确认密码。

登录完成后可以立即体验不需要代码仓库的功能。用户添加仓库时，再按需连接 GitHub 仓库并选择仓库。不要为了进入平台，强制要求用户授予私有仓库读写权限。

已有密码账号的用户先通过原方式登录，再明确选择「绑定 GitHub 登录」。绑定后仍保留原有项目、历史运行、权限和凭据。

### 登录与代码访问的边界

| 用途 | 结果 | 凭据处理 |
| --- | --- | --- |
| 登录平台 | 解析 GitHub 用户身份，建立或查找平台账号，签发平台自己的会话 Cookie | 不把仅用于登录的令牌写入 GitToken，不覆盖已有仓库凭据 |
| 绑定登录方式 | 在当前已登录且重新验证过的用户与 GitHub 身份间建立关联 | 必须显式确认，不能通过同名或相同邮箱自动合并 |
| 连接仓库 | 在当前用户明确同意后取得代码访问能力，列出可访问仓库 | 仓库令牌保留在用户凭据域，按实际返回的权限判断可用能力 |

这两类用途可以使用同一个 GitHub OAuth App，并共享授权客户端、设备码、错误处理等基础设施；账号关联、平台会话、授权目的与令牌存储需要分别处理。不能把「取消仓库授权」解释为删除平台账号，取消平台登录绑定也不应隐式删除仓库凭据。

### OAuth 网页跳转与 PIN 的选择

- 固定域名的平台优先使用网页 OAuth：点击按钮、在 GitHub 同意、回到平台。注册无需另一个表单。服务端配置 Client ID、Client Secret、受信任回调地址，并校验 state、PKCE、浏览器发起状态和授权用途。
- 自部署实例可提供 PIN 登录：无需为任意用户域名配置网页回调，也无需分发 Client Secret；复用当前设备码授权能力。
- PIN 需要显示、复制和输入设备码，不等于免输码的一键网页登录。文案应明确「使用设备码登录」，避免承诺与实际操作不一致。
- 同一个固定网页回调不能直接覆盖所有自部署域名。若未来提供统一登录中转服务，需要单独设计实例注册、受信任跳转和会话交付，不在当前本地授权方案中隐含引入。
- 当前仓库连接已内置维护方注册的 LoopForge 应用公开 Client ID，不要求用户自行创建应用；这不代表本文提议的 GitHub 注册和登录已经实现。不得借用其他工具的 Client ID 或让用户填写 PAT 作为登录前置条件。

### 当前代码需要调整的地方

1. `internal/httpapi/github_auth.go` 当前要求已登录，并将授权结果直接保存到该用户的 GitToken。该流程是仓库连接，不能直接当成注册入口。
2. 现有待授权记录以平台 user ID 为键。匿名登录必须绑定独立、短期、不可预测的浏览器发起状态，不能让所有匿名用户共用 user ID 0，也不能只凭浏览器提交的 GitHub 用户名或 flow ID 建立平台会话。
3. `internal/httpapi/auth_tokens.go` 需要明确放行 GitHub 登录能力查询、登录开始和回调/轮询端点；这些端点自行验证来源、会话状态和授权目的。仓库连接仍要求已登录，不能整体放开认证相关 API。
4. 在 UsersRepo 增加持久化外部身份映射，以 provider 与 GitHub 返回的数字 user ID 标识身份，并建立唯一约束。GitHub login、显示名和邮箱都不能作为自动关联已有账号的依据。Github 改名后也不能生成重复平台账号。
5. `authSetup` 和 `authRegister` 目前只看 `LocalAccountCount()`。直接新增 GitHub 注册会导致已有 GitHub 账号时仍被判断为首次部署，后续密码注册可能错误取得管理员。应统一初始化状态和首位管理员判定，并保证跨登录方式、跨 API 实例并发时只产生一名初始化管理员。
6. GitHub 自动建号必须服从现有注册开关。关闭注册时，已绑定账号仍可登录；未知身份不能自动加入实例。GitHub 身份验证成功不等于获得该部署的访问权限。
7. 沿用平台现有用户 ID、项目归属、权限与签名 Cookie。后续 GitHub 登录不重新创建账号，不重置角色，不覆盖其他执行器凭据。用户名冲突应明确处理，不能静默接管同名本地账号。
8. 登录授权与仓库令牌刷新分别处理。仓库令牌撤销或过期时显示「重新连接仓库」，不应让平台账号和本地密码一起失效。解除最后一种可用登录方式前要求设置替代登录方式。

新增模型遵循 UsersRepo 领域归属；只使用现有增量建表机制或显式 SQL，不增加启动时的数据迁移和 seed。

### 界面安排

- 登录页：有可用 GitHub 配置时显示推荐按钮；未配置时保留密码入口，明确说明管理员尚未启用 GitHub 登录。不要出现点击后才报 503 的主按钮。
- 配置具备网页回调时使用网页 OAuth；只有设备码配置时展示设备码流程和清楚的操作说明。
- 首次登录：不强制配置模型 Key 或仓库，先给出免 Key 示例和可选的下一步。
- 个人配置：分别显示「GitHub 登录已绑定」与「GitHub 仓库已连接」，说明切换/解绑影响。
- 仓库选择：未连接时提供授权入口；已具备所需仓库权限时直接选择仓库，避免无意义的重复授权。GitHub 仓库选择只决定项目绑定，不代表缩小 OAuth repo 授权范围。

### 验收重点

- 全新 GitHub 身份完成注册和登录；同一身份重复登录仍是同一用户；GitHub 改名不改变平台用户 ID。
- 同名本地账号不会被合并或接管；从本地账号绑定已归属其他用户的 GitHub 身份时明确拒绝。
- 登录授权不会把低权限令牌写入 GitToken 或覆盖现有仓库授权。
- 多个匿名浏览器、多个标签页、回调重放、用户拒绝、超时和服务重启均有确定结果。
- 关闭注册后未知 GitHub 身份无法自动注册；已有绑定用户正常登录。
- 密码注册与 GitHub 注册同时发生时，首次管理员判定正确；Github-only 部署不再显示首次密码初始化。
- 网页 OAuth 与设备码使用同一身份映射；仓库授权使用明确不同的授权目的。
- 真实 Client ID 配置后，分别验证真实网页登录、真实 PIN 登录和真实仓库选择；未配置时不声称已完成真实验收。

### 结论

**身份校验能阻止换号，但“cleanup 再刷新一次以确认 refresh token 的归属”尚不适合直接作为三种 CLI 的通用实现。**

在模拟认证服务的契约下，原型保留正常轮换和后续刷新，能拒绝整套换号、伪造本地身份、
只换 refresh token、只换 access token、同工作区不同用户、同用户不同组织。
这些结果证明的是算法在明确假设下的行为，不是真实供应商兼容性认证。

同时复现了两个会影响正常续期的边界：

1. 服务端已经轮换 refresh token，但响应在客户端收到之前丢失。隔离保存的仍是已消耗的
   旧 token，无法恢复客户端从未收到的新 token；直接重试还可能触发 token 重用检测。
2. 两个沙箱或宿主机 CLI 使用同一份一次性 refresh token。第二次使用可以导致认证服务
   撤销整个 token family。宿主机文件的内容比较与原子 rename 不能撤销服务端的变化。

因此，先前“遇到网络错误就隔离并重试，可以避免丢失轮换凭证”的说法需要收窄：
**只有已经收到、并持久化了新凭证，之后的身份查询失败，才验证了可在重启后安全恢复。**

#### Codex 三方同时刷新的具体解释

上面的严格一次性 token / family 撤销模拟，不能直接等同于 Codex 服务端的实际策略。
[OpenAI 维护者于 2026-02-01 的解释](https://github.com/openai/codex/issues/10332)指出，
其刷新服务允许旧 refresh token 在有限宽限期内多次使用，当时描述为约一小时量级。
这是维护者对当时实现的说明，不是当前时长或所有轮换细节的稳定契约；本次未用真实账号验证。

两个 SOP 与宿主机同时从同一份原凭证刷新，在该宽限机制下可以各自成功，不能断言只有
一个成功、另两个必定退出登录。当前 LoopForge 给 SOP 的是各自私有 HOME 内的文件副本，
不是三方共享同一个宿主机认证文件。若宿主机先保存新凭证，两个 SOP 后续 cleanup 会发现
宿主机已经不同于最初快照并跳过写回；SOP 不会因此自动收到宿主机的最新凭证。

仍需单独验证的正常路径是：沙箱早已复制了旧凭证，宿主机已刷新，沙箱却在宽限结束后才
首次用旧 refresh token 刷新。独立 HOME 无法通过重新读取自己的文件获得宿主机更新，
当前 cleanup 的内容比较也不能协调运行中的刷新。不能仅增加 cleanup 锁就声称解决了
两个 SOP 与宿主机 CLI 之间的刷新协调。

### 第一轮执行结果

### 补充验证：官方刷新接口与真实 Antigravity

#### Codex 0.163.0：官方外部认证接口可用

按照[官方 App Server 文档](https://developers.openai.com/codex/app-server/)使用实验性
`chatgptAuthTokens` 登录和 `account/chatgptAuthTokens/refresh` 回调。启动三个私有 HOME
的官方 CLI，模拟宿主机与两个任务都接入同一个 Runner 刷新入口。三方最初只拿 access token，
本机模拟服务分别拒绝旧 token 后，三个 CLI 都回调宿主。

结果：**3 次认证拒绝 → 3 次回调 → 1 次模拟发行端刷新 → 3 个 CLI 恢复**。
Runner 先原子保存并 fsync 发行端返回的新凭证，再交付 access token；三个 CLI 的私有 HOME
都没有拿到 Runner 保管的 refresh token。这是官方客户端与模拟发行端的协议实测，未使用
当前 Codex 账号。没有证明不接入 Runner 的其他宿主机 CLI 也能被这把锁协调。

#### Claude Code 2.1.326：有回调实现，但受入口限制

检查官方发布的 `@anthropic-ai/claude-agent-sdk@0.3.326` JavaScript 和本机官方 CLI，
发现 `getOAuthToken` / `oauth_token_refresh` 路径；**公开的 sdk.d.ts 未声明此选项**。
本机 CLI 还检查客户端入口：普通 `sdk-ts` 没有启用这条回调，允许的内部入口包括 `local-agent`。

全部在隔离 HOME、虚构凭证与本机模拟服务下实测，无 Claude 订阅、无真实 Anthropic 调用：

- 普通 `sdk-ts` 负对照：收到模拟 401 后回调数为 0，认证失败。
- 显式测试内部 `local-agent` 路径：**3 次模拟 401 → 3 次宿主回调 → 1 次模拟刷新 →
  3 次模型请求重试成功**。模型响应由本机夹具生成，没有消费订阅或 API 额度。

这证明当前客户端有可工作的协议实现，**没有证明它是稳定公开 SDK 契约，也没有完成真实
Claude 订阅、组织归属或服务端刷新策略验收**。内部入口仅用于隔离实验，正式实现不能把
未经确认的内部能力当成无条件支持。

#### Antigravity 1.5.10：真实 Google 并发刷新成功

`TestWritebackProbeAntigravityLiveRefresh` 显式 opt-in 后读取本机既有 Antigravity 钥匙串
记录。只调用官方 `agy models`，通过让私有副本的 access token / expiry 失效触发真实刷新；
不修改宿主原件使其过期、不触发交互登录、不调用付费模型推理。

| 真实场景 | 结果 |
| --- | --- |
| native 单次前置刷新 | 成功，18 个模型，refresh token 未变化 |
| 两路 native + 一路 Docker 同用旧 refresh token 并发刷新 | 三路全部成功，各返回 18 个模型，refresh token 均未变化 |
| 三路完成后再用同一个 refresh token 刷新 | 成功，refresh token 仍未变化 |
| 删除 refresh token，只保留有效 access token，native 查询模型 | 成功，18 个模型 |
| 同样的 access-only 文件，Docker 查询模型 | 成功，18 个模型 |
| 最终 access token 向 Google OIDC userinfo 查询身份 | 成功，不记录账号标识 |

此处“宿主侧”是隔离的 native 凭证副本；验证的是同一个真实 Google refresh token 的
并发重用行为，没有把用户正在使用的外部宿主 CLI 改接到新的管理器。native / Docker 都是
直接执行官方 CLI，没有重新创建完整对话或 SOP 业务任务。

有效刷新结果保留到原钥匙串来源；检测到宿主源已更新且 refresh token 相同，保留宿主更新。
模型查询失败也先检查是否已生成需要保留的新凭证。所有并发进程收集结束后才清理私有副本。
Docker 使用宿主 HOME 下缓存目录的私有临时子目录和严格 bind mount；未共享的 macOS /tmp
不能被误当作已经挂载的凭证目录。测试目录 `0700`、凭证 `0600`，成功后全部删除，不写入镜像或仓库。

**结论只适用于本次账号、版本与请求范围**：没有观察到“刷新一次立即作废旧 refresh token”。
这降低了本次并发导致掉登录的担忧。access-only 查询成功还不能证明长任务中的 token 热更新、
token 到期后的自动恢复，或未来的服务端轮换策略。

#### 补充实验的隔离方式

`scripts/probe-cli-auth-control.py` 为 Codex / Claude 创建临时证书和仅本机的模拟服务。
Claude 的官方主机名由本机夹具模拟，用来进入客户端第一方 OAuth 分支；代理绝不向外转发，
子进程同时由 macOS 禁止访问外网和真实认证目录。证书只传给测试子进程，不修改系统信任。
这不是生产认证代理方案。Antigravity 的真实测试在另一个进程运行，没有使用该代理或测试 CA。

### 测试中的验证器

这是 `_test.go` 内的实验，不是待发布的生产验证器：

1. 在复制凭证前，向可信身份服务确认宿主机的主体、工作区、组织，保存 Runner 私有基准。
   本地已过期凭证如何建立这一基准，尚需各 CLI 的具体协议解决。
2. 将候选文件保存到沙箱之外的 Runner 私有状态。示例目录 `0700`、文件 `0600`，
   临时文件写入后 `fsync`、rename、目录 `fsync`。身份基准与原文件快照都不由沙箱提供。
3. 未变更的候选直接跳过，不额外刷新。宿主机已更新或已登出，直接放弃写回。
4. 候选 access token 若能验证，先拒绝不同主体。access token 已失效则不以此判断归属。
5. **兑换候选 refresh token**，保存认证服务返回的完整新凭证，再核实新 access token 的身份。
   这一步才会暴露“access 属于 A、refresh 属于 B”的混合凭证。
6. 身份一致且宿主机仍未变更，写回服务端返回的新凭证，绝不写回已经被再次兑换的沙箱凭证。
   响应未给新 refresh token 时保留兑换时使用的 token，不把它清空。
7. 新凭证已持久化、身份服务暂时故障：恢复后只查询身份，不重复兑换旧 refresh token。
   刷新请求结果不明：标记 `uncertain`，不盲目重试，也不声称已恢复自动续期。

测试还保留 Claude 的 scopes、subscriptionType、rateLimitTier 等字段，并验证写回后的
凭证能在下一次模拟 CLI 调用中继续刷新。

## AgentFlow 前端预览与交付物生命周期方案

> 状态：待评审  
> 基线：`master@4ee2db5`（2026-09-19）  
> 目标读者：负责 Engine、Runner、HTTP API、Studio 和基础设施的开发 Agent  
> 核心原则：**Workspace 是生产过程，Preview 是交付资产。**

### 1. 背景

当前 AgentFlow 已支持在 Run 详情中通过内嵌 VS Code 浏览运行工作区，但成功交付后会立即清理工作区。这个行为对后端任务合理；对前端任务而言，如果预览依赖工作区和开发服务器继续存在，成功后预览也会一起消失。反过来，如果为了预览长期保留 workspace，又会把源码、`.git`、依赖、缓存、CLI Home 和 Docker writable layer 一起保留，磁盘成本不可控。

正确的抽象不是“前端 Run 不清理 workspace”，而是：

```text
运行中的 Workspace
      ↓ 交付收尾
提取 Preview Artifact
      ↓
销毁 Workspace / Sandbox
      ↓
保留轻量、受控、有 TTL 的 Preview
```

### 2. 当前 master 的事实

#### 2.1 工作区与 UI

- Run 详情已有“工作区”Tab，通过 `/vscode.html?run=...` 嵌入只读 VS Code。
- VS Code 通过 `/api/runs/:id/workspace/*` 读取目录、文件、diff、日志和搜索结果。
- 工作区可能位于控制面，也可能位于 Runner；Runner 工作区通过现有控制通道读取。
- `workspaceCleanedAt` 一旦设置，UI 和 API 都明确显示工作区已删除。

相关代码：

- `web/app.js`：`vscodeWorkbenchURL`、`workspacePaneHTML`。
- `web/vscode.js`：只读 VS Code workbench。
- `internal/httpapi/run_workspace.go`：工作区读取和 Runner 转发。

#### 2.2 成功后的清理

- Run 进入 `succeeded` 或 `cancelled` 后立即调用 `cleanupRunWorkspace`。
- 清理先将 `workspace_cleaned_at` 设为当前时间，使工作区立即不可再访问。
- 本地执行时销毁 Docker container、临时 image 和 workspace。
- Runner 执行时创建持久化 `cleanup_run` task，在 Runner 上删除容器和 `runs/<runId>`。
- 失败 Run 保留 workspace，供原地重试；重新派发后会回收旧容器。

相关代码：

- `internal/engine/engine.go`：`finish`、`cleanupWorkspace`。
- `internal/repo/runs.go`：`TerminalWorkspaceCleanupRuns`、`ClaimRunWorkspaceCleanup`。
- `internal/runtime/sandbox_manager.go`：`DestroyRun`。
- `internal/runner/daemon.go`：`executeRunCleanup`。

#### 2.3 现有 Artifact 不能承载网站构建产物

现有 `run_artifacts` 面向 Markdown/JSON 等小型不可变报告：

- 内容存储在 MySQL `LONGTEXT`。
- Runner 完成接口最多 64 个文件。
- Runner 单文件最大 1MB。
- `ArtifactContract` 只描述单文件路径。
- 目前没有 blob/object storage 抽象、目录打包上传或二进制下载通道。

因此不能把 `dist/` 简单塞进现有 `run_artifacts.content`。

### 3. 目标

1. 成功 Run 仍能及时删除 workspace 和开发 sandbox。
2. 纯静态前端交付后可以长期或按 TTL 预览。
3. 预览内容和 AgentFlow 主站隔离，不能读取平台 Cookie、LocalStorage 或调用平台 API。
4. 本地执行和 Runner 执行使用同一种 Preview 元数据与存储协议。
5. 预览生成失败默认不改变业务交付结果，但必须可见；工作流可显式配置为必需。
6. 预览有容量、文件数、TTL、闲置停止、按项目配额和审计。
7. 为 SSR、服务型前端和复杂全栈环境保留演进路径，但 MVP 不为此永久保留 workspace。

### 4. 非目标

- MVP 不自动猜测任意项目的构建命令。
- MVP 不扫描监听端口并选择“最大的端口”。
- MVP 不把完整 workspace 打包成预览。
- MVP 不直接把容器 IP 暴露给浏览器。
- MVP 不在 AgentFlow 主站同源路径下执行不可信 HTML。
- MVP 不支持永久运行的预览容器。
- MVP 不把 Docker 本地 image 当作跨机器的长期交付资产。

### 5. 分层生命周期

```text
Hot：Run 正在执行
- 完整 workspace
- Sandbox / Docker container
- VS Code
- 可选开发服务器
- 生命周期跟随 Run

Warm：Run 已交付，可交互预览
- workspace 已删除
- static bundle 或 OCI image
- screenshot
- preview metadata
- TTL / quota / idle stop

Cold：预览已过期
- Git commit / MR / patch
- Run logs / telemetry
- 普通不可变 artifacts
- screenshot（可选长期保留）
- Preview bundle/image 已删除
```

建议默认策略：

| 类型 | Warm 资产 | 默认 TTL | 运行资源 |
|---|---|---:|---|
| 后端任务 | 无 | 0 | 成功后立即清理 |
| 静态 SPA | 压缩后的静态 bundle + screenshot | 30 天（硬上限） | 无常驻容器 |
| SSR/Node 服务 | OCI image + screenshot | 3 天 | 按需启动，闲置 10 分钟停止 |
| 复杂全栈 | Preview Environment bundle | 24 小时 | 显式启动、严格配额 |
| 已固定/Pin | 按项目策略保留 | 最大 30 天或管理员策略 | 仍受容量上限 |

所有默认值必须可配置，不应写死在前端。

### 6. 总体架构

```text
WorkflowSnapshot.preview
        |
        v
Run 完成节点执行
        |
        v
Preview Finalizer
  |-- 校验 PreviewContract
  |-- 本地或 Runner 打包
  |-- 上传 PreviewStore
  |-- 可选截图
  |-- 写 run_previews
        |
        v
Preview 状态进入 ready / failed
        |
        v
释放 cleanup hold
        |
        v
现有 workspace/sandbox 清理
        |
        v
Studio 获取短期 Preview Session
        |
        v
独立 preview origin 提供静态内容或反向代理
```

核心新增组件：

1. `PreviewContract`：随 WorkflowSnapshot 冻结的交付契约。
2. `PreviewFinalizer`：Run 成功与 workspace 清理之间的收尾阶段。
3. `PreviewStore`：二进制/目录交付物存储接口。
4. `run_previews`：预览元数据与状态。
5. `Preview Gateway`：独立 origin 的访问入口。
6. `Preview GC`：TTL、容量和孤儿资源清理。
7. Runner 的 preview archive/upload 内置 action。

### 7. PreviewContract

建议在 `domain.WorkflowDefinition` 增加 Run 级别的预览契约，并随 `WorkflowSnapshot` 冻结：

```go
type PreviewContract struct {
    Enabled      bool   `json:"enabled"`
    Kind         string `json:"kind"`          // static；后续 service/environment
    SourcePath   string `json:"sourcePath"`    // run workspace 相对路径
    IndexFile    string `json:"indexFile"`     // 默认 index.html
    SPAFallback  bool   `json:"spaFallback"`
    Required     bool   `json:"required"`
    CaptureShot  bool   `json:"captureScreenshot"`
    RetentionSec int64  `json:"retentionSec,omitempty"`
}
```

MVP 只接受 `kind=static`。

#### 7.1 为什么不在 Finalizer 自动运行 npm build

构建属于工作流行为，应由可观测、可重试的 script/agent node 完成。Preview Finalizer 只负责验证和归档声明的目录，不执行模型生成的任意命令。

推荐 SOP：

```text
实现节点
  ↓
测试节点
  ↓
前端构建节点：npm ci && npm run build
  ↓
Preview Finalizer：归档 repo/dist
  ↓
工作区清理
```

这样构建日志和失败原因进入正常 Run 轨迹，构建失败可走现有 retry/onFailure，Finalizer 也不需要重新注入 Git、npm 或业务密钥。

#### 7.2 路径规则

- `SourcePath` 必须是 run workspace 内的相对路径。
- 多仓库任务必须明确带目录，例如 `frontend/dist`。
- 禁止绝对路径、`..`、空路径和符号链接越界。
- 归档时拒绝 symlink、hardlink、device、socket 和 FIFO。
- 必须存在 `IndexFile`。
- 默认最大 20,000 个文件、压缩包 100MB、展开后 500MB；可配置但受平台硬上限约束。

### 8. 数据模型

新增独立表，不复用 `run_artifacts.content`：

```sql
CREATE TABLE run_previews (
  id VARCHAR(64) PRIMARY KEY,
  run_id VARCHAR(64) NOT NULL,
  project_id VARCHAR(64) NOT NULL DEFAULT '',
  kind VARCHAR(32) NOT NULL,
  status VARCHAR(32) NOT NULL,
  source_path VARCHAR(1024) NOT NULL DEFAULT '',
  storage_key VARCHAR(1024) NOT NULL DEFAULT '',
  content_sha256 CHAR(64) NOT NULL DEFAULT '',
  compressed_size BIGINT NOT NULL DEFAULT 0,
  expanded_size BIGINT NOT NULL DEFAULT 0,
  file_count INT NOT NULL DEFAULT 0,
  entry_file VARCHAR(512) NOT NULL DEFAULT 'index.html',
  spa_fallback TINYINT(1) NOT NULL DEFAULT 0,
  owner_runner_id VARCHAR(64) NOT NULL DEFAULT '',
  screenshot_key VARCHAR(1024) NOT NULL DEFAULT '',
  error_text TEXT,
  last_accessed_at DATETIME(3) NULL,
  expires_at DATETIME(3) NULL,
  created_at DATETIME(3) NULL,
  updated_at DATETIME(3) NULL,
  UNIQUE KEY uq_run_previews_run (run_id),
  KEY idx_run_previews_status_expiry (status, expires_at),
  KEY idx_run_previews_project (project_id, created_at)
);
```

状态建议：

```text
pending -> archiving -> ready -> expired -> deleting -> deleted
pending/archiving -> failed
pending -> skipped   # 工作区没有前端工程，不失败主流程
```

后续服务型预览再增加 `starting -> running -> stopped`。不要把容器 ID、动态端口当作长期真值；它们属于短期 Preview Session。

### 9. PreviewStore

定义独立接口：

```go
type PreviewStore interface {
    Put(ctx context.Context, key string, src io.Reader, size int64, sha256 string) error
    Open(ctx context.Context, key string) (io.ReadSeekCloser, PreviewObject, error)
    Delete(ctx context.Context, key string) error
}
```

实现顺序：

1. `DBPreviewStore`
   - tar.zst 存在 MySQL `preview_blobs`，按 SHA-256 去重。
   - 任意 API 实例按请求从库中取出成员，不依赖本机目录或 `AGENTFLOW_PREVIEW_ROOT`。
2. COS/S3 PreviewStore
   - 后续生产可选。
   - 支持分段上传、服务端加密和生命周期规则。
   - 数据库存 metadata，不保存大对象正文。

相同内容可通过 SHA-256 去重，但删除需要引用计数或在 GC 中确认没有其他 ready preview 引用。

### 10. 成功收尾与 workspace cleanup hold

当前 `finish(succeeded)` 会立即调用 cleanup。需要在该位置引入 Preview Finalizer，避免归档和删除竞态。

#### 10.1 无 PreviewContract

保持当前行为：`succeeded -> immediate cleanup`。

#### 10.2 有 static PreviewContract

```text
Run 标记 succeeded
  -> 创建 run_preview(status=pending)
  -> 建立 preview cleanup hold
  -> 异步/任务化归档
  -> ready 或 failed
  -> 释放 hold
  -> 调用现有 cleanupRunWorkspace
```

不要长期增加新的 Run 业务状态；Run 可以已经 `succeeded`，预览单独显示“生成中”。但 workspace 清理查询必须识别 hold。

建议增加通用字段 `runs.workspace_cleanup_not_before`，同时 `cleanupWorkspace` 在 claim 前检查：

- 是否有 `pending/archiving` preview。
- 是否超过 preview finalization 最大时限。
- 是否已有清理任务在执行。

默认 finalization 超时建议 15 分钟。超时后：

- `Required=false`：preview 标记 failed，继续清理，Run 保持 succeeded。
- `Required=true`：应通过显式构建/验证节点在 Run 成功前失败，不建议在已 succeeded 后反转状态。

为避免服务重启后泄漏，startup/sweep 必须恢复 pending preview、超时 hold，以及 ready/failed 后遗漏的 workspace cleanup。

### 11. 本地执行归档

控制面本地 sandbox：

1. 从 `Manager.RunWorkspace(runID)` 定位 workspace。
2. 在受限 walker 中读取 `SourcePath`。
3. 校验文件数、类型和展开大小。
4. 以确定顺序打包为 `tar.zst`，mtime/uid/gid 归一化，保证相同内容 hash 稳定。
5. 流式写入 `PreviewStore`，不把整个 bundle 读入内存。
6. 更新 preview metadata 为 ready。
7. 清理 workspace/container。

归档代码不能调用 shell `tar` 处理不可信路径，优先使用 Go `archive/tar` 和受控压缩库。

### 12. Runner 执行归档

现有 Runner artifact 完成接口只支持 JSON 字符串和 1MB 单文件，不能复用。

新增 Runner 内置 action：`archive_preview`。

任务携带：

```go
type RunnerPreviewArchiveSpec struct {
    PreviewID   string
    RunID       string
    SourcePath  string
    IndexFile   string
    MaxFiles    int
    MaxBytes    int64
    UploadURL   string
    UploadToken string
}
```

流程：

1. Engine 在 run 成功后向原 Runner 创建 `archive_preview` task。
2. Runner 在 `runs/<runId>` 下安全解析 SourcePath。
3. Runner 流式生成归一化 `tar.zst`。
4. Runner 使用一次性 upload token 上传到控制面专用端点。
5. 控制面边接收边计算 hash、限制压缩大小并写 PreviewStore。
6. 完成后 preview 进入 ready，Engine 再排队现有 `cleanup_run`。
7. 失败可重试，任务 ID 必须确定性且幂等。

建议端点：

```text
PUT  /runners/previews/:previewId/content
POST /runners/previews/:previewId/complete
```

要求：

- 使用 Runner session + preview upload token 双重约束。
- token 绑定 previewId、runId、runnerId、最大字节和过期时间。
- 不把大文件放进 runner_tasks JSON payload。
- 上传中断不得留下可见的 ready 对象。
- 先完成 PreviewStore 原子提交，再更新数据库。

Runner 离线时，preview 显示“等待执行机器上线”。超过 finalization timeout 后按非必需失败处理并释放 cleanup hold，不得为了预览无限保留 Runner workspace。

### 13. Preview Gateway 与安全边界

#### 13.1 路径托管，不用独立 Origin

未配置 wildcard DNS 的部署不能使用 `https://<token>.preview.example.com/`。当前 MVP 使用同 Host 路径：

```text
https://loopforge.example.com/preview/<session-token>/
```

不要再引入 `AGENTFLOW_PREVIEW_ENABLED`、`AGENTFLOW_PREVIEW_ROOT`、`AGENTFLOW_PREVIEW_BASE_DOMAIN`。预览默认开启；静态包进 MySQL；`AGENTFLOW_PREVIEW_PUBLIC_URL` 只覆盖对外 origin（例如反代后的 `https://loopforge.example.com`）。

预览 HTML 仍是不可信内容。用短期 token、CSP `sandbox` + `connect-src`、以及运行时拦截 fetch/XHR 来约束它能访问的后端。主站 API 不在预览 token 路径下。

#### 13.2 访问会话

Studio 调用 `POST /api/runs/:id/preview/session`。服务端验证用户对 Run 的读取权限后创建短期随机 session，返回完整 preview URL。

建议：

- token 至少 128 bit 随机值，数据库只存 hash。
- 默认 30 分钟过期，可在 iframe 活跃时续期。
- token 绑定 previewId，不放用户信息。
- 设置 `Referrer-Policy: same-origin`：带 token 的预览地址只会作为 Referer 发给本站，第三方和 `backendUrl` 收不到。网关据此把预览页发往根路径、而 history 垫片没有接住的整页导航（新标签页打开的链接、POST 表单、不支持 Navigation API 的浏览器里的 `location.href`）303 回 `/preview/<token>/` 下；页面自带的 `<meta name="referrer">` 一律改写为 `same-origin`。
- 访问记录只记 token hash 前缀，不记完整 URL。
- 会话可带 `backendUrl`；网关注入并拦截跨站/`/api` 请求转到该 origin。

#### 13.3 iframe

```html
<iframe
  src="/preview/<token>/"
  sandbox="allow-scripts allow-forms allow-modals allow-downloads allow-same-origin"
  referrerpolicy="no-referrer"
></iframe>
```

路径托管下必须开 `allow-same-origin`，否则 Vite ESM 无法加载。不要添加 `allow-top-navigation`。剪贴板、摄像头、麦克风和定位默认不授权。

代价是预览与平台同源：预览脚本可以操作外层 Studio 页面（读写 DOM、借 `parent.fetch` 以当前登录用户身份调平台接口），CSP 的 `connect-src` 只约束预览文档自身。

#### 13.4 静态响应

- 禁止目录列表。
- 精确 MIME 类型，并设置 `X-Content-Type-Options: nosniff`。
- HTML 只允许配置的 AgentFlow 主站 `frame-ancestors`。
- 静态 hash 资源可 immutable cache，HTML 使用 no-cache。
- `SPAFallback=true` 时，未命中文件且 Accept 包含 HTML 才回退 index。
- 在 `</head>` 前注入 history 垫片：SPA 路由按 `/` 写入的地址会被收回 `/preview/<token>/` 下。网关扫描预览包，只有用到 `pushState`/`replaceState` 的包才在启动时把地址临时换成去掉前缀的路径，直到路由第一次写 history 或注册 `popstate` 监听（兜底为 load 后 10 秒）；前进后退时只在事件分发期间去掉前缀。没有路由的包地址始终带前缀。
- 垫片把发往前缀外同源路径的整页跳转直接改到前缀下：左键点击链接（所有浏览器），以及 `location.href`/`replace`/`reload()` 和 GET 表单（Navigation API）。离开前先把当前历史记录恢复成带前缀的地址，后退时不会回到平台。
- 拒绝编码穿越、双重编码、NUL 和软链接。
- 不允许预览内容通过响应头设置 Cookie。
- screenshot/preview fetch 不携带平台凭据。

路径托管下 `location.pathname` 只有一个值：应用要的是 `/about`，地址栏、刷新和 Referer 要的是 `/preview/<token>/about`。垫片只能在一段时间内二选一，已知限制：

- 业务代码在启动后直接读 `location.pathname`，读到的是带前缀的路径。
- 有路由的包在路由启动前，独立窗口地址栏显示去掉前缀的地址，这时用浏览器刷新或复制地址会落到平台；load 后 10 秒仍未启动的路由会读到带前缀的路径。
- 启动期间在新标签页打开链接、提交 POST 表单，以及不支持 Navigation API 的浏览器里的脚本跳转，仍会落到平台。

独立 preview host 可以自然解决绝对 `/assets/*`、前端路由和 service worker base path 问题，比 path-based proxy 兼容性更高。

### 14. Studio 交互

Run 详情 Tab：

```text
[概览] [实时轨迹] [Worker日志] [工作区] [前端预览] [智能评测]
```

状态：

- 未配置：不展示 Tab，或显示“该 SOP 未声明前端预览”。
- `pending/archiving`：显示生成进度和来源路径。
- `ready`：显示 iframe、独立窗口、刷新和复制预览地址。
- `failed`：显示脱敏错误，不影响普通交付物查看。
- `expired`：显示 screenshot、过期时间和“重新构建”入口（后续能力）。
- Runner 离线：显示不可用原因和最终超时时间。

工作区与预览必须明确区分：

- “工作区”：运行过程、只读代码、跟随 workspace 生命周期。
- “前端预览”：交付结果、独立资产、跟随 Preview TTL。

前端不要根据 Run 状态猜测预览是否存在，统一读取 `GET /api/runs/:id/preview`。

### 15. Screenshot

Screenshot 是预览的降级展示，不应依赖 workspace 长期存在。建议在 preview ready 后由独立 screenshot worker：

1. 使用 Playwright 打开 Preview Gateway URL。
2. 等待 network idle 或最多 15 秒。
3. 使用固定 viewport（例如 1440×900）。
4. 保存 PNG/WebP 到 PreviewStore。
5. 写 `screenshot_key`。

截图失败不影响 preview ready。即使 bundle 过期，截图可以跟随 Run 更长时间保留。不要在 Agent 运行容器内安装浏览器来截图，这会增加 sandbox image 和 writable layer。

### 16. 服务型预览：Phase 2

静态预览稳定后再支持 Next.js SSR、Nuxt SSR 和 Node 服务。

#### 16.1 交付物

不要保留原 sandbox container。应生成并推送 OCI image：

```text
workspace
  -> docker/buildkit build
  -> push preview registry
  -> record immutable image digest
  -> delete workspace and build container
```

必须配置专用 registry，不能仅保留 Runner 本地 image；否则 Runner 卸载、换机或磁盘清理后预览不可恢复。

可增加：

```go
type ServicePreviewContract struct {
    DockerfilePath string
    BuildContext   string
    ContainerPort  int
    HealthPath     string
    StartupTimeout int
    IdleTimeout    int
}
```

#### 16.2 按需启动

用户打开预览：

1. 创建 `PreviewRuntimeSession`。
2. 选择原 Runner 或专用 preview runner。
3. pull 固定 digest。
4. 启动无凭据、只读 rootfs、资源受限的 container。
5. 等待健康检查。
6. Preview Gateway 代理 HTTP/WebSocket。
7. 无访问 10 分钟后停止 container。

#### 16.3 Runner 隧道

远程 Runner 的容器 IP 对浏览器不可达。应扩展现有 Runner WebSocket control channel，增加多路复用 preview tunnel：

```text
Browser
 -> Preview Gateway
 -> runner control websocket
 -> Runner local reverse proxy
 -> preview container:port
```

协议需要 request/session ID、HTTP headers/body stream、WebSocket binary stream、背压、取消和限速。不要把完整 HTTP body 塞进单条 JSON control message。

本地控制面执行可以使用 `httputil.ReverseProxy`；两条路径应共享同一授权和 header 清洗策略。

#### 16.4 代理要求

- 支持 WebSocket Upgrade。
- 清洗 hop-by-hop headers、`Set-Cookie`、`Location` 和外部重定向。
- 限制请求/响应 body、连接数、带宽和最长连接时间。
- 默认禁用出站网络或使用预览专用 egress policy。
- 不注入 Run 的 Git、CodeBuddy 或 MCP 凭据。
- 容器使用独立网络、非 root、drop capabilities、no-new-privileges。

### 17. Full-stack Preview Environment：Phase 3

前端 + 后端 + MySQL/Redis 已经是临时部署，不是普通前端预览，必须显式 opt-in：

- 独立 Preview Environment 定义。
- 使用合成测试数据或声明式 seed，禁止复制生产数据库。
- 默认 TTL 24 小时。
- 项目级并发和总容量限制。
- 到期强制销毁计算、volume、DB 和缓存。
- 仅保留 screenshot、metadata、日志和构建摘要。

该阶段建议使用 Kubernetes/OpenSandbox，而不是继续扩展单机 Docker 特例。

### 19. GC、配额与幂等

后台周期任务处理：

- `expires_at <= now` 的 ready/failed preview。
- 数据库无引用的 PreviewStore 对象。
- uploading 临时文件。
- 已停止但未删除的 runtime container。
- registry 中无引用的 preview image。
- 超时的 workspace cleanup hold。

删除顺序：`标记 deleting -> 停止 runtime -> 删除 blob/image/screenshot -> 标记 deleted`。每一步必须幂等，可在进程重启后继续。

至少提供：

- 单 preview 压缩/展开大小。
- 单项目 preview 总字节。
- 单用户并发归档数。
- 单项目运行中 service preview 数。
- Runner 上传速率。
- Preview Gateway 并发连接和带宽。
- 最大 TTL 与 Pin 权限。

超过配额时 preview 失败，但默认不回滚已成功的业务 Run。

### 20. 可观测性

Run timeline 事件：

```text
preview.archive.queued
preview.archive.started
preview.archive.uploading
preview.archive.ready
preview.archive.failed
preview.session.started
preview.session.stopped
preview.expired
preview.deleted
```

指标：

- preview 生成成功率和耗时 P50/P95。
- bundle 压缩/展开大小。
- 每项目存储用量。
- session 启动耗时、活跃 session、闲置停止次数。
- Gateway HTTP 5xx / WebSocket 断开。
- preview hold 延迟 workspace 清理的时长。

日志不得包含完整访问 token、敏感 header 或预览页面正文。

### 23. 测试矩阵

#### 23.1 归档安全

- 正常 Vite/React `dist/`。
- SPA history fallback。
- 空目录、缺 index、超大文件、超多文件。
- symlink/hardlink/pipe/device。
- `../`、绝对路径、URL 编码穿越、双重编码。
- 打包过程中 workspace 被修改或删除。
- 相同内容生成相同 hash。
- 归档不包含 `.git`、目录外文件和凭据。

#### 23.2 生命周期

- 无 preview 的成功 Run 保持立即清理。
- preview ready 后才清理 workspace。
- preview failed/timeout 后释放 hold。
- cancelled Run 不生成 preview 并立即清理。
- failed Run 保持现有 retry workspace。
- 服务重启恢复 pending archive 和 cleanup。
- 重复 finalizer、Runner completion、GC 均幂等。

#### 23.3 Runner

- archive task 只能访问 `runs/<runId>`。
- Runner/Run/Preview/token 不匹配拒绝。
- 上传中断与重试。
- 超限时服务端中止读取。
- Runner 离线后超时释放 workspace。
- preview 成功后才下发 `cleanup_run`。

#### 23.4 Gateway 安全

- Preview 与主站 origin 不同。
- 预览脚本无法调用 AgentFlow API。
- session token 过期、撤销、猜测失败。
- 无目录列表、无 symlink 逃逸。
- MIME、nosniff、CSP、frame-ancestors、Referrer-Policy。
- 主站 Cookie 不发送到 preview host。
- 跨项目用户无法创建访问 session。

#### 23.5 UI

- building/ready/failed/expired 状态。
- iframe 与独立窗口。
- 工作区已清理但预览仍可用。
- preview 过期但 screenshot 可见。
- Run 切换时销毁旧 iframe/session。

### 24. 验收标准

静态 MVP 默认开启前必须满足：

1. 成功前端 Run 的 workspace 和 Docker sandbox 仍按现有策略删除。
2. `dist/` 在 workspace 删除后仍可预览。
3. 本地与 Runner Run 都能生成相同类型的 preview。
4. 预览页面与主站严格跨 origin，无法读取或使用主站身份。
5. 绝对 `/assets/*`、SPA 路由和常见静态框架可正常工作。
6. 归档失败不会无限阻塞 workspace 清理。
7. 大文件、路径穿越、symlink 和压缩炸弹被拒绝。
8. TTL 到期会回收 blob，数据库状态可审计。
9. feature flag 关闭后完全恢复当前行为。
10. 不把 preview 二进制写入 MySQL `run_artifacts.content`。

### 25. 给实施 Agent 的执行顺序

1. 先实现 `PreviewContract`、`run_previews` 和 `PreviewStore`，不要先做 iframe。
2. 为当前 `finish -> cleanup` 写失败测试：有 pending preview 时 workspace 不得被删除。
3. 完成本地 static archive，并验证 ready 后触发现有 cleanup。
4. 实现独立 preview origin 和安全测试，再接 Studio Tab。
5. 实现 Runner 流式 archive/upload，禁止走现有 1MB artifact JSON。
6. 增加 GC、配额和重启恢复。
7. 静态链路稳定后再设计 service preview tunnel；不要在 MVP 中混入动态端口扫描和 Docker 运行时代理。

首轮产品行为采用以下默认值。这些是本方案的设计选择，实施评审时可以调整。

- **写操作默认只读。** 新建 Bot（**包括新建的企微 Bot**）默认 `writeApproval=readonly`。企微历史记录缺少该字段时，继续映射现有的自动执行策略。新渠道收到写请求时，引导用户到项目页面操作。新建企微 Bot 从“自动执行”改为“只读”属于管理员能感知到的变化，写入上线说明和 `CHANGELOG.md`，见第 12 节。
- **配置归属与执行权限。** 一个 Bot 配置固定归属一个项目。绑定用户的执行权限来自其平台账号和当前项目。即使 Bot 由平台管理员创建，普通成员发来的消息仍按该成员的权限执行。
- **聊天范围。** 飞书、钉钉首轮只处理私聊文本，群消息计数后直接结束处理。企微已有的群聊和卡片按原协议继续工作。
- **接收配置唯一。** 同一 LoopForge 部署中，一个企业应用只能启用一个接收配置。不同环境需要配置各自独立的机器人应用。租约在同一部署的数据库范围内协调。
- **未绑定用户。** 未绑定的用户先收到网页绑定链接，在网页上确认现有 LoopForge 账号，再由原 IM 发送者提交 `/bind <code>`。绑定成功后，用户需要重新发送业务请求。
- **回复形式。** 企微保留现有的流式进度。飞书、钉钉首轮只返回最终文本；处理时间较长时，另发一条接单提示，提示有独立的记录和投递 key。
- **网页登录。** 网页绑定使用 LoopForge 现有的登录能力。企业 SSO 可以作为已有登录入口使用。

本分支按第 11 节的 IM-01 至 IM-12 验收。三个渠道的真实联调分别记录证据。

### 4. 渠道接口与运行规则

#### 4.1 接收、回复与主动发送

渠道适配器放在 `internal/botinteraction` 包内，这样企微适配器可以直接包装已有的未导出 socket 方法。公共编排只处理领域事件和发送结果。下面的签名已在阶段 A 落地（`channel.go`）。

```go
type Channel interface {
    Kind() string
    Verify(context.Context, domain.NotificationBot, Credential) (Verification, error)
    Connect(context.Context, domain.NotificationBot, Credential, InboundSink) (Conn, error)
}

type Conn interface {
    Done() <-chan struct{}
    Reply(context.Context, OutboundMessage) SendResult
    Close() error
}

// 返回 Accepted=true 表示本次事件新建了交互；重复事件返回 Accepted=false 且 err 为 nil。
// 返回 err 时适配器按平台协议回失败确认，让平台重投。
type InboundSink func(context.Context, InboundEvent) (InboundAck, error)

// 主动通知通过应用 API 发送，实例只需持有通知投递租约。
type PushSender interface {
    Push(context.Context, domain.NotificationBot, Credential, OutboundMessage) SendResult
}

type SendOutcome string

const (
    Delivered    SendOutcome = "delivered"
    NotDelivered SendOutcome = "not_delivered"
    Rejected     SendOutcome = "rejected"
    Unknown      SendOutcome = "unknown"
)

type SendResult struct {
    Outcome           SendOutcome
    Code              string
    Retryable         bool
    PlatformMessageID string
    SafeDetail        string
}
```

第 2 版写的 `InboundSink` 只返回 `error`，第 3 版改为同时返回 `InboundAck`。原因是企微要在“新建交互成功”之后才发出“已收到，正在处理…”的接单流式消息，重复事件不能再发一次。

`InboundEvent` 包含以下内容：

- **消息字段：** 业务消息 ID、平台事件 ID、发送者、会话、聊天类型、消息类型、正文和引用；
- **可信事件字段：** 适配器从可信事件中读取的应用标识、企业范围和回复路由；
- **企微专用字段：** 卡片动作、投递 ID、卡片 task ID 和请求 ID。

服务端以当前连接对应的 Bot 配置决定项目、模型和权限，不信任事件中自带的项目信息。

`OutboundMessage` 包含：

- 内部交互或投递 ID；
- 冻结的目标；
- 正文；
- 是否为最终回复；
- 持久化的 `send_key`；
- 回复路由。

日志和公共 DTO 只使用脱敏后的信息。

企微的流式进度和卡片通过可选接口提供（`progressConn`、`cardConn`），飞书、钉钉首轮只用普通文本回复。

`PushSender` 由渠道对象实现，与 `Conn` 相互独立。阶段 A 中，企微的 `Push` 包装注入的 `wecom-cli` 发送函数；通知服务仍按原路径直接调用 `Provider`，到阶段 G 再切换到 `PushSender`。

企微的凭据校验复用 `CLIProvider` 的签名鉴权：阶段 A 新增 `CLIProvider.Verify`，由 `notification.New` 把它显式注入企微渠道。校验只调用鉴权接口，不建立短暂的验证连接，因此不会挤掉正在运行的接收连接。

#### 4.2 身份和连接范围

JSON 中的 `botId` 继续作为外部应用标识。新增渠道字段 `channel`，取值为 `wecom`、`feishu`、`dingtalk`。

| 标识 | 历史企微 | 飞书、钉钉 |
| --- | --- | --- |
| 配置 ID | `NotificationBot.ID` | `NotificationBot.ID` |
| 外部 ID | 原 `BotID` | App ID / Client ID |
| 身份范围 `IdentityScope()` | 原外部 Bot ID | 内部配置 ID |
| 平台消息去重 | `BotMessageID(bot.IdentityScope(), messageID)` | `BotMessageID(bot.IdentityScope(), messageID)` |
| 内部卡片交互 ID | 保持 `BotMessageID(bot.ID, "notification:"…)` | 首轮不生成卡片 |
| 会话 ID | 保留现有派生规则（内部配置 ID、聊天类型、Chat ID） | 使用相同派生函数 |
| 接收占位 `ReceiveSlot()` | 对渠道和外部 ID 做稳定派生 | 对渠道和外部 ID 做稳定派生 |
| 连接租约 `LeaseKey()` | 原外部 Bot ID | 接收占位值 |

`ReceiveSlot` 采用 `channel + ":" + hex(sha256(externalID))`，长度小于现有列的 191 字符上限。只有在 `enabled && interactionEnabled` 时才写入这个唯一列，其余情况写 SQL `NULL`。

**创建后不可改的字段：** 配置 ID、渠道、外部应用 ID 和项目。企业范围按第 8.2、8.3 节先确认，进入 `locked` 状态后同样固定。

- 修改名称、模型、启停，或更换同一应用的 Secret，使用更新接口。
- 切换项目或应用，需要新建配置并重新绑定。
- 旧客户端提交时缺少 `channel`，一律按企微处理；新客户端必须明确提交渠道。

绑定的读取、创建挑战、确认、解绑、平台消息去重和助手执行，统一调用 `IdentityScope()`。企微的旧绑定继续按原键访问。

`bot_connections.bot_id` 存的是 `LeaseKey()`：

- 企微行存原外部 Bot ID；
- 飞书和钉钉行存 `ReceiveSlot()`，即 `channel:hex(sha256(externalID))`，例如钉钉为 `dingtalk:<Client ID 的 SHA-256 小写十六进制>`。

连接的领取、续约、释放、状态查询，以及第 7.1 节中按连接行加锁的参数，都统一传 `bot.LeaseKey()`。而 `bot_interactions.bot_id` 继续存内部配置 ID。这两列分别表示连接租约和配置归属，不能混用。

#### 4.3 配置、凭据与重连

**保存流程。** Secret 的校验放在数据库事务之外完成。保存请求携带预期的 `configVersion`，事务内按第 7.1 节的锁顺序先锁配置行，比较版本，再原子更新配置和密文；版本冲突返回 `409 config_changed`。

**两个版本号。** 两者都是 `notification_bots` 上的物理列，payload 中同步保存一份用于展示：

| 版本号 | 递增时机 | 不递增的情况 |
| --- | --- | --- |
| `config_version` | 每次成功写配置：名称、模型、启停、写策略、企业锁定、目标变更 | 记录 `tenantCandidate` 等候选字段 |
| `credential_version` | 只在 Secret 变更时 | — |

**重连只看连接相关字段。** 接收服务比较以下字段的指纹：渠道、外部应用 ID、`credential_version`、`enabled`、`interaction_enabled`。指纹变化才关闭旧连接并重连。现有 `reconcile` 用 `UpdatedAt` 判断是否重连，阶段 B 改为比较这个指纹。

因此，企业锁定、改名称和模型只会增加 `config_version`，不会触发重连；从下一条事件或下一轮执行开始按新值校验。出站发送每次都重新读取配置和当前凭据。

停用和删除的状态处理见第 7.2 节。删除 Bot 的事务还会撤销该配置的挑战和绑定。对历史企微按外部 ID 关联的绑定，先核对是否还有其他保留的配置使用同一身份范围。历史记录中的 Secret 和会话 Webhook，在取消或进入终态后的清理中移除。

#### 5.2 数据库时间

所有租约、发送窗口、重试时间和路由有效期，**写入和判断都使用数据库时间**，Go 进程的墙钟只用来决定何时在本地提前取消。

- **存储格式。** 这些字段以 epoch 微秒存为 `BIGINT`，列名带 `_us` 后缀，避免 MySQL `DATETIME` 与 SQLite 文本时间在格式和时区上的比较差异。
- **方言函数。** `internal/repo/dbtime.go` 提供 `dbNowUS(db)`，返回当前方言的 SQL 表达式：
  - MySQL：`CAST(UNIX_TIMESTAMP(NOW(6)) * 1000000 AS SIGNED)`，与会话时区无关；
  - SQLite：`CAST(ROUND((julianday('now') - 2440587.5) * 86400000000.0) AS INTEGER)`。
- **写入与判断都在 SQL 内。** 写入时用 `SET lease_until_us = <dbNowUS> + 45000000`，判断时用 `lease_until_us > <dbNowUS>`。Go 端不传入当前时间值。
- **测试。** 阶段 B 为该函数单独写测试，覆盖 SQLite 下的写入、比较、跨秒边界和 `OpenTest` 时间注入；MySQL 测试覆盖相同的断言。可控时钟测试通过替换 `dbNowUS` 表达式为固定值实现。
- **展示列。** 原有的 `DATETIME` 列（如 `lease_until`）保留，在同一语句中一并写入，仅用于展示和兼容，不参与判断。

#### 5.3 凭据加密

`internal/credcrypt` 使用标准库的 AES-256-GCM，每次加密生成随机 nonce。

**密钥配置。** 通过 `AGENTFLOW_CREDENTIAL_KEYS` 注入，格式为 `kid:base64(32字节)[,kid:base64(32字节)]`，第一把是当前写入密钥。

**密文格式。** 封装为 `lf1:<kid>:<base64(nonce || ciphertext)>`。凭据内容序列化为 `{"secret":"..."}`，AAD 编码配置 ID 与渠道。会话 Webhook 的 AAD 编码配置、交互 ID 和字段用途。

**读写规则：**

- 历史明文仍可读取，管理页标记为“待迁移”。
- 带 `lf1:` 前缀的数据必须按密文解析，解密失败直接返回错误。
- 新写入需要有效密钥；密钥缺失时返回 `503 credential_key_missing`。

**迁移命令。** 增加运维子命令 `-credential-action status|reencrypt`，通过显式指令逐条迁移旧明文或旧 kid 密文，记录成功、跳过和失败的数量。命令可以重复执行。密钥解析和 Repo 注入使用现有的装配入口，日志只记录 kid 和计数。

#### 5.4 手动迁移顺序

遵守 `AGENTS.md` 中“增量 DDL 与手工数据迁移”的约定。生产 MySQL 是验收数据库，SQLite `OpenTest` 用于服务测试。

1. **备份与只读检查。** 备份数据库和原版本二进制。先跑只读检查，列出重复启用的企微配置、孤立绑定和无法判断归属的绑定。
2. **停旧副本，以维护模式启动新版本。** 先停止**全部**旧版本副本。`AGENTFLOW_BOT_WORKERS_ENABLED` 是阶段 B 新增的开关，旧版本二进制不认识它，所以不能指望旧版本靠这个开关暂停 worker。然后以 `AGENTFLOW_BOT_WORKERS_ENABLED=false` 启动一个新版本实例。开关关闭时：
   - 对话和通知两个后台入口都不启动；
   - Bot 配置的写接口返回 `503 bot_maintenance`；
   - 启动时的增量 DDL 补齐缺失的表、列和索引，`receive_slot` 初始为 `NULL`。
3. **运行 `036` 回填段。** 填写渠道、外部应用 ID、接收占位、物理启停列和版本列。缺少渠道的旧值统一识别为企微。回填前先处理重复占位；脚本失败时事务回滚。
4. **运行 `037` 归属查询。** 明确匹配的，回填绑定和挑战的 `config_id`。多个配置共用旧企微身份的记录，保留清单，按真实启用的配置确认归属。
5. **重新加密凭据。** 所有副本配置相同的 Keyring，执行显式的 `reencrypt`，复核计数。
6. **恢复服务。** 以 `AGENTFLOW_BOT_WORKERS_ENABLED=true` 重启全部新版本副本。先验证企微，再依次启用飞书和钉钉。

**脚本补充说明：**

- `036` 同时补齐 `bot_native_sessions` 的基线 DDL 和交互的项目归属快照。
- `037` 对历史原生会话单独输出“可证实映射”和“待核查”两份清单；映射证据不足的记录标记为待核查。
- 脚本先确认所需的列存在再引用；DDL 与回填分段执行，出错即停止。
- MySQL 版本兼容性通过目标测试镜像验证，按 schema 检查生成明确的手工 DDL。
- 迁移前后记录表行数、绑定归属计数和冲突数。

**升级与回退。** 升级完成后，所有运行中的副本使用同一套新租约协议。凭据加密完成后，回退的二进制必须具备相同的解密能力；如果要退回更旧的版本，使用升级前的备份，并按停机窗口核对期间新增的业务数据。

### 6. 入站、绑定与业务权限

#### 6.1 公共入站流程

处理链路：`SDK 事件 → 校验当前配置与应用/企业 → 分类 → 事务入队 → 平台确认 → worker 执行`。阶段 A 已把“由事件生成交互并入队”提取到 `inbound.go` 的 `Service.accept`；企微、模拟渠道以及后续的飞书、钉钉适配器都经过这个入口。

**确认时限。** 飞书 handler 只做校验和有界的数据库事务，要留在官方约 3 秒的确认窗口之内，因此入队操作设置短超时。

**确认结果。** 入库成功和重复事件都正常确认。数据库写入失败时，handler 返回错误；飞书固定版本 SDK 会据此回复 500，平台随后重投（见第 8.2 节）。 [飞书长连接](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-) · [飞书事件重投](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/event-subscriptions)

**去重。** 业务去重键是 `IdentityScope + 平台业务消息 ID`，平台事件 ID 另存，便于排查。平台重投时即使事件 ID 不同，同一业务消息也只执行一轮。接单提示同样通过持久化记录发送，与最终回复使用不同的 key。

**输入限制：**

- 新渠道文本上限暂定 8000 个 Unicode 字符。
- 非文本和超长输入只记录类型与长度，并按限频提示用户；正文在进入助手之前完成分类。
- 企微沿用已有的输入与历史限额。
- 同一个 Bot 的同一会话串行处理。

#### 6.2 两阶段绑定

1. 未绑定的私聊发送者收到 `/bot-bind.html#request=<nonce>`。服务端只保存 nonce 的哈希，有效期 15 分钟。
2. 网页通过现有的 `/api/auth/current` 登录，显示渠道、Bot 名称、项目、脱敏后的发送者，以及将要绑定的账号。
3. 用户确认后，页面发起同源 POST `/api/bot-bindings/claim`。服务器保存短期确认码的摘要，页面显示 `/bind <code>`。
4. 用户在原 IM 中发送确认码。适配器从原 Bot 的可信事件中读取发送者；公共处理校验配置范围、原发送者、有效期和确认码摘要，在同一事务中写入绑定并消费挑战。
5. 绑定成功后提示用户重新发送业务请求。挑战、确认码和绑定指令在进入模型和构造历史之前剔除。

**解绑与复核。** 沿用现有的 `/unbind` 命令和个人配置中的解绑入口。状态 API 和确认 API 都会复核：配置存在、Bot 已启用、当前账号有效、有项目访问权限。绑定页只接受同源写请求，授权依赖网页登录会话。

**限频：**

- 引导消息默认 10 分钟最多发 3 次；用户主动获取新链接每分钟最多 1 次；计数使用原子更新。
- 已有有效挑战时，提示用户查看上一条链接。
- 旧链接只存了哈希，无法重新生成；用户主动获取新链接时，作废旧挑战并创建新挑战。

#### 6.3 执行业务和只读约束

`botExecutionUser` 每轮都读取当前配置和绑定，核对：用户存在、Bot 状态、项目成员权限、配置版本。每次工具调用仍经过平台原有的权限检查。绑定有效性和工具授权在执行边界再验证一次，以覆盖执行过程中被解绑或撤权的情况。

阶段 D 在 `assistantExecMode` 中加入明确的只读标记，并贯穿工具目录、工具网关和终态草稿处理：

- **平台工具。** 只读工具继续按项目权限开放；写工具在工具目录和执行网关两处按同一策略拒绝。
- **外部 MCP 和原生工具。** 按真实能力分类，只开放已确认为只读的能力。CLI 命令、文件写入和其他具有写入能力的工具，在只读模式下一律拒绝。
- **写草稿。** 模型产生写草稿时，回复“请在平台页面确认操作”。新增渠道首轮只通过只读助手完成状态查询。
- **模型凭据。** 使用绑定用户自己的模型凭据；用户未配置密钥时提示其配置，不回退到 Bot 创建者的身份。
- **提示词边界。** 模型输入保留角色层级和用户原始消息，提示词中的输入标记用于区分材料来源。写权限和目标校验都在服务端实施，不依赖提示词。

用三类真实项目查询验证上述策略：项目状态、SOP 进度、本人待办。首批真实验收使用普通项目成员账号。

### 7. 连接租约与发送状态机

#### 7.1 锁顺序、连接与交互归属

**锁顺序固定为：配置 → 连接 → 交互/投递。** 同一类表有多行时，按主键升序加锁。所有带归属条件的写操作（保存结果、开始发送、写回发送结果、写卡片 task ID、切换会话、恢复、停用、删除、人工补发、人工确认）都在一个事务内按以下步骤执行：

1. `SELECT … FROM notification_bots WHERE id = ? FOR UPDATE`：读物理列 `enabled`、`interaction_enabled`、`config_version`。
2. `SELECT … FROM bot_connections WHERE bot_id = <bot.LeaseKey()> FOR UPDATE`：检查 `owner`、`epoch`，以及 `lease_until_us > <dbNowUS>`。删除、停用和人工操作没有连接 owner，只加锁，不比较 owner。
3. 按条件更新交互或投递行，检查 `RowsAffected`。

```sql
-- 第 3 步示例（MySQL）；第 1、2 步已在同一事务内持锁
UPDATE bot_interactions
SET status = ?, updated_at = ?
WHERE id = ?
  AND status = ?
  AND lease_owner = ?
  AND lease_epoch = ?;
```

第 1、2 步任一条件不满足，或第 3 步更新了 0 行，就返回 `ErrLeaseLost` 或明确的状态冲突，执行循环随即停止本地工作。SQLite 没有行锁，以数据库级写锁串行化；`r.locking(tx)` 在 SQLite 上不加子句，测试中语义相同。阶段 C 的评审清单逐个核对每条写路径的加锁顺序；MySQL 测试用两个并发事务复现“删除”与“写回结果”的交错，确认不会死锁。

**连接租约。** 继续采用 45 秒 TTL、10 秒续约，写入和判断按第 5.2 节使用数据库时间。

- owner 变更或租约过期后重新领取时，原子递增 `epoch`；同一个有效 owner 续约时保持 epoch 不变。
- 领取交互时保存 `lease_owner`、`lease_epoch` 和 `config_version`。连接相关的 Repo 方法统一以 `bot.LeaseKey()` 为键；领取交互时的配置过滤条件使用 `bot.ID`。

**续约失败与恢复。** 接收副本续约失败时，关闭连接，并取消模型和发送的上下文。恢复时：

- 旧 epoch 下的 `running` 记录，写入现有提示“执行已中断，请核查结果”；
- `ready` 记录继续投递已保存的结果。

#### 7.2 回复发送、重试和终态

```text
queued → running → ready → sending → replied
             └──中断──→ ready（中断说明）

sending → 明确未送达，未达重试上限      → ready（next_send_at_us，保留正文和 key）
sending → 明确未送达，已达重试上限      → reply_failed（undelivered_exhausted）
sending → 平台明确拒绝                  → reply_failed
sending → 送达未知（飞书，窗口内）      → ready（同一 key，按窗口退避）
sending → 送达未知（飞书窗口已到期 / 企微 / 钉钉） → reply_unknown
ready   → 回复路由过期                  → reply_failed（route_expired）
reply_unknown / reply_failed → 人工再次发送 → ready（generation + 1，新 key）
reply_unknown → 人工确认已收到          → replied（receipt_source=manual）

queued              → 停用 / 删除 → cancelled（bot_disabled / bot_deleted）
running             → 停用 / 删除 → cancelled，并向本地任务发送取消信号；执行记录保留
ready               → 停用        → 保持 ready（暂存，停用期间不领取）
ready               → 删除        → cancelled（bot_deleted，正文保留在记录页）
sending             → 停用 / 删除 → reply_unknown（bot_disabled_during_send / bot_deleted_during_send）
```

**两类自动重试分开处理：**

| 结果 | 判断依据 | 处理 |
| --- | --- | --- |
| `Delivered` | 平台确认该回复成功 | 记为 `replied`，保存回执。该状态只表示平台确认已发送 |
| `NotDelivered` | 有证据表明请求未提交，或平台明确表示未发送且可重试 | **按次数重试**：首次失败后最多自动重试 3 次，间隔 5 秒、30 秒、2 分钟，`undelivered_retries` 单独计数；耗尽后转 `reply_failed`（通知转 `failed`）。所有渠道一致，重试沿用同一个 key |
| `Rejected` | 平台明确拒绝 | 直接转 `reply_failed`，显示安全错误码。已核对过的限流码或可刷新的鉴权错误，按 `NotDelivered` 处理 |
| `Unknown` | 请求可能已写出：读回执超时、网络中断，或进程在发送阶段退出 | **飞书**：按固定 key 和时间窗口恢复（第 7.3 节），不计入 `undelivered_retries`；窗口到期转 `reply_unknown`。**企微、钉钉**：直接转 `reply_unknown`（通知转 `send_unknown`） |

发送步骤：

1. 领取 `ready` 记录，复核绑定、项目、当前配置和回复路由。复核以当前配置为准，要求应用身份、企业范围和启用状态有效，不要求与生成回复时的 `config_version` 相等。这样停用期间暂存的回复，重新启用后仍可发送。
2. 按第 7.1 节的锁顺序原子写入：`sending`、当前 generation 的首次 `send_started_at_us`（只在为空时写）、发送次数、短发送租约 `send_lease_until_us`。`send_key` 在首次生成回复时就已持久化。
3. 事务提交后再调用 SDK，网络操作不在事务内。单次发送超时 10 秒；发送前要求连接租约至少还剩 15 秒。
4. 按平台回执和请求证据分类，带条件写回结果和平台消息 ID。

**送达证据。** `WriteJSON` 报错时请求可能已部分写出；HTTP 5xx 也可能出现在平台已经处理请求之后。因此分类依据实际的请求证据，不看错误类型。现有企微“流式失败就主动再发一次”的路径，阶段 C 起只在确认未送达时才启用备用发送。

**换主时的发送窗口。** `sending` 状态的交互被新 owner 接管时，保留它原有的发送占用窗口。新 owner 要等原发送租约到期、再加上预留的时钟偏差之后，才执行平台幂等恢复或转为待核对。外部 IM 接口无法检查数据库 epoch，所以靠发送窗口、固定 key 和未知状态三者共同防止重复发送。

**停用与删除。** 停用和删除事务都按锁顺序执行：

- **迟到写回。** 成功写回先提交的，交互保留 `replied`、通知保留 `sent`；停用或删除先提交的，`sending` 记录转为 `reply_unknown` 或 `send_unknown`。旧 worker 迟到的写回会因状态、租约或配置校验失败而停止，迟到的回执写入独立审计。
- **删除后的待核对记录。** 仍可人工核对、确认已收到；人工再次发送返回 `409 bot_deleted`。删除事务清空回复路由、发送租约和旧的写回凭据，保留正文、generation、key 和已有回执。对话记录保存项目归属快照，项目管理员可以从项目记录页继续查看。
- **停用期间暂存的回复。** 记录页显示“停用期间暂存”。重新启用后，回复路由仍有效的正常发送，已过期的转 `reply_failed`（`route_expired`）。
- **停用对通知的影响。** 沿用现有行为：领取时发现停用，记为 `cancelled`；处于 `sending` 的转为 `send_unknown`。

#### 7.3 固定 key 与人工处理

**固定 key。** 首次生成回复时，持久化一个随机 UUID 或等价的不透明 key。自动重试从数据库读取同一个 key、正文和目标。

**飞书恢复窗口。** 飞书的 `uuid` 参数提供一小时的请求去重窗口，本方案以当前 generation 的“首次 `send_started_at_us` + 55 分钟”作为恢复上限：

- **时钟。** 首次时间值由数据库时间写入，恢复和重试资格也用同一个数据库时钟计算。自动重试、连接易主、进程重启都不重置这个值。
- **每次发送前检查。** 每次调用 SDK 前都重新检查窗口，并要求单次请求的超时也落在上限之内。
- **退避。** 窗口内依次按 5 秒、30 秒、2 分钟退避，之后最多每 2 分钟一次；到截止时刻转 `reply_unknown`。

[飞书固定版本 SDK 的回复去重字段](https://github.com/larksuite/oapi-sdk-go/blob/v3.13.0/service/im/v1/model.go)

**SDK 自身的重试。** 适配器显式设置 SDK 和 HTTP 客户端的重试策略，确保底层重试沿用同一个 key。没有平台幂等保护的发送，由公共状态机决定是否重试，并关闭 SDK 的自动重发选项。

**记录页操作。** 企微和钉钉在缺少已验证的平台幂等能力时，`Unknown` 一律进入 `reply_unknown`。记录页分别提供“确认已收到”和“再次发送”两个操作，“再次发送”会明确提示可能重复。

**人工再次发送：**

- 只接受 `reply_unknown` 或 `reply_failed` 状态的记录。
- 在事务内校验：操作权限、Bot 和绑定有效、目标和路由仍可用。
- 校验通过后：状态改为 `ready`，`delivery_generation += 1`，生成新 key，重置发送次数、`undelivered_retries`、`next_send_at_us`，并把当前 generation 的 `send_started_at_us` 置空（首次进入 `sending` 时由数据库填写）。
- 留下操作人和原因，只投递已保存的结果，之后由正常的发送 worker 领取。
- 请求的 action key 去重覆盖状态更新，重复点击返回同一个 generation。

**人工确认已收到：**

- 交互从 `reply_unknown` 改为 `replied`，通知从 `send_unknown` 改为 `sent`。
- 写入 `confirmed_by`、数据库时间 `confirmed_at` 和 `receipt_source=manual`，界面显示“人工确认”。
- 相关审计字段在阶段 C 一并加入交互和通知模型。

**冲突返回。** Bot 已删除时，人工再次发送返回 `409 bot_deleted`；路由已过期时返回 `409 route_expired`。路由过期的钉钉回复，到阶段 G 后可改用主动单聊补发，见第 9.2 节。

### 8. 三个渠道的实现细节

#### 8.1 企业微信

**接收。** 阶段 A 起由 `channel_wecom.go` 包装 `dial`、`socket.request`、`stream` 和卡片更新。`socket.request` 的错误现在带有发送阶段，分类规则如下：

| 情况 | 分类 |
| --- | --- |
| 写出前失败 | `NotDelivered` |
| 写出失败，或已写出后回执超时、连接关闭、上下文取消 | `Unknown` |
| 平台返回非 0 错误码 | `Rejected` |

阶段 A 只把分类结果映射回原有行为，用户可感知的行为不变：

- `Delivered` 记为已发送；
- `Rejected` 记为发送失败；
- 其他情况断开重连，之后重发 `ready` 记录；
- 流式失败后仍然备用发送一次。

**主动通知。** 继续沿用官方 CLI 的会话发现、目标校验和授权状态。

**兼容回归固定以下内容：**

- 历史外部 Bot ID、绑定 ID、消息 ID、租约 key 的派生结果；
- 私聊、群聊、群内 @、新会话命令与流式进度；
- `waiting`、`failed` 通知卡片的服务端 task ID 和操作者授权检查；
- 主动通知的目标发现、授权过期处理和最终文本；
- 同 key 的平台回执、连接中断、发送结果未知和人工补发。

#### 8.2 飞书

**依赖版本。** 官方 `github.com/larksuite/oapi-sdk-go/v3@v3.13.0`。阶段 A 已在 Go 1.26.11 下用探针模块验证，结论如下：

- `ws.Client.Start(ctx)` 会阻塞，context 取消后返回 `context canceled`；
- 提供 `Close` 和 `CloseAndWait`；
- 事件 handler 返回错误时，SDK 回复 500，平台据此重投；
- `ReplyMessageReqBody.Uuid`、`CreateMessageReqBody.Uuid`、`tenant/v2` 的 `Query` 均可编译；
- govulncheck v1.9.0 未发现漏洞。

依赖在阶段 E 首次实际使用时写入主模块的 `go.mod`、`go.sum` 和 `THIRD_PARTY_NOTICES.md`，避免 `go mod tidy` 移除尚未使用的依赖。 [飞书 Go SDK](https://github.com/larksuite/oapi-sdk-go)

| 环节 | 实施约定 |
| --- | --- |
| 应用 | 企业自建应用，开启机器人、单聊接收和发送权限，发布给试点成员 |
| Verify | 用 App ID / Secret 获取 `tenant_access_token`，验证凭据。企业归属进入 `awaiting_confirmation`，按下文流程锁定 |
| 企业信息辅助 | 用应用令牌调用 `GET /open-apis/tenant/v2/tenant/query`（官方“获取企业信息”接口，自建应用可用，频率上限 1000 次/分钟）。固定版本 SDK 的 `Tenant` 模型包含 `tenant_key`、企业名称和 display_id。查询结果只作为确认页的辅助信息，与事件候选值并排展示；接口失败（如 `1184001` 无权限）不阻断流程。所需权限以开放平台应用后台的显示为准 |
| Connect | 官方长连接客户端加消息事件 dispatcher，设置 `WithAutoReconnect(false)`，由公共连接循环负责重连。`Start` 返回时关闭 `Conn.Done()`，`Close` 调用 `CloseAndWait` |
| 事件 | `header.app_id`、`header.tenant_key`、`event_id`、`message_id`、`sender.open_id`、`chat_id`、`chat_type`、`message_type`、文本 JSON |
| 原会话回复 | Message Reply 接口，传原 `message_id`、文本和已持久化的 `send_key`（作为 `uuid`） |
| 主动通知 | Message Create 接口，使用当前 Bot 已验证的目标，带独立的投递 key |
| 鉴权与限流 | 从 SDK 返回中提取平台错误码，建立明确的可重试名单；遇到未知错误码时保守地停止自动重发，并显示可诊断的原因 |

**企业确认流程（`tenantState`）。** 飞书和钉钉共用这套状态：`awaiting_confirmation` → `locked`，异常时为 `conflict`。

1. 新配置通过 Verify 后保存 `tenantState=awaiting_confirmation`。接收配置照常占用唯一的 ReceiveSlot，连接可以接收用于发现企业的事件。管理页显示“等待企业确认”。
2. 适配器从当前凭据认证的 SDK 连接中，读取 App ID 匹配、`tenant_key` 非空的首个消息事件，保存 `tenantCandidate`、事件 ID、接收时间和当时的凭据版本。**写候选字段不增加 `config_version`。** 该事件到此结束：
   - 不创建绑定或业务交互；
   - 通过一条持久化提示记录回复发送者：“机器人正在完成企业确认，请稍后重发消息。”
   - 出现不同的候选值时，状态转为 `conflict`，显示冲突诊断，等待管理员重新发起发现。
3. Bot 管理员在同源页面确认候选企业：POST `/api/notification-bots/:id/tenant/confirm`，携带候选值和 `configVersion`。事务检查候选来源、当前凭据版本、管理权限，然后写入固定的 `tenant_key`、确认人、数据库确认时间，状态变为 `locked`，`config_version` 加一。因为第 2 步没有改版本号，管理员页面拿到的版本仍然有效；锁定也不触发重连（见第 4.3 节）。
4. 锁定后，提示测试用户重新发送业务消息。之后接收的每个事件都必须与固定值匹配。轮换同一应用的凭据时保留锁定范围，并继续检查事件归属。要更换应用或已锁定的企业范围，需新建配置。
5. 阶段 E 的适配器测试、HTTP 测试和真实测试覆盖：发现前、候选已采集、确认并发、凭据轮换、锁定后跨企业消息被拒绝。已取到令牌但尚未锁定的 Bot，在 UI 和 API 中持续显示“企业待确认”。

飞书事件样例需覆盖：企业或应用不匹配、同一消息不同投递 ID、应用范围内的 `open_id`、短事务失败、SDK 关闭。接收方使用 `open_id` 时保留其应用范围。 [飞书身份范围](https://open.feishu.cn/document/platform-overveiw/basic-concepts/user-identity-introduction/introduction)

#### 8.3 钉钉

**SDK 只用一部分。** 依赖为官方 `github.com/open-dingtalk/dingtalk-stream-sdk-go@v0.9.1`，这是当前最新的稳定版，另有 `v0.9.2-beta.1`。阶段 A 的探针验证发现以下问题，因此**阶段 F 不使用 SDK 的 `StreamClient` 连接循环和 `ChatbotReplier`**：

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| 心跳超时后再收到一帧，未恢复的 panic 会使进程退出 | 探针中服务端不回 pong，10 秒后推送一帧文本，子进程以 `send on closed channel` 退出（exit 2）。原因是 `processLoop` 退出时关闭了 `readChan`/`closeChan`，而读协程和 pong 超时协程仍会向它们写入 | 宿主进程整体崩溃，所有项目的服务中断 |
| `Start` 建连不接受 context | 内部调用 `dialer.Dial`，而不是 `DialContext` | 停止时可能卡住 |
| 自动重连使用 `context.Background()` 无限循环 | `reconnect` 实现 | 调用 `Close` 后仍可能重新连上，形成僵尸连接 |
| `ChatbotReplier` 使用默认重定向策略、固定 5 秒超时，200 响应未关闭 body | `ReplyMessage` 实现 | 违反“禁止重定向”约定，并泄漏连接 |

阶段 F 只采用该 SDK 中经过验证、无副作用的部分：

- 用 `payload.ConnectionEndpointRequest/Response` 获取接入点（实施时改为自建请求：SDK 的 `GetConnectionEndpoint` 挂在 `StreamClient` 上，使用默认传输和重定向策略，与本节的 HTTP 约定不符）；
- 用 `payload` 包解析 DataFrame、构造确认帧；
- 用 `chatbot.BotCallbackDataModel` 解析事件。

WebSocket 读写循环、心跳和重连由适配器基于主模块已有的 `gorilla/websocket v1.5.3` 实现，与企微连接的生命周期一致。

会话 Webhook 和主动发送使用自建的 HTTP 客户端：禁止重定向，设置明确超时，限制响应读取长度。如果上游修复了上述问题并发布稳定版，再评估是否改回 SDK 循环。

**凭据校验。** 该 SDK 不提供 access token 接口，Verify 直接调用官方 `POST https://api.dingtalk.com/v1.0/oauth2/accessToken`。 [钉钉 Stream Go SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-go)

| 环节 | 实施约定 |
| --- | --- |
| Verify | 用官方 accessToken 接口校验 Client ID / Secret |
| 企业确认 | 复用第 8.2 节的 `tenantState`。管理员必须手填企业 CorpId，作为预期值保存，状态为 `awaiting_confirmation`。首个可信事件的企业字段与预期值一致时，自动转为 `locked`，记录事件 ID 和数据库时间，确认人记为填写 CorpId 的管理员，`config_version` 加一；不一致时转为 `conflict`，不处理业务，由管理员修正后重新发现。等待确认期间的消息回复与飞书相同的提示 |
| Connect | 自建 Stream 读写循环，注册机器人回调 topic；事件入库成功后回复成功确认帧，入库失败时回复错误帧 |
| 发送者 | 优先读取经过验证的 `senderStaffId`，与当前企业范围组合；字段缺失时拒绝业务执行并记录诊断 |
| 事件 | `msgId`、`conversationId`、`conversationType`、`chatbotCorpId`、`senderCorpId`、`msgtype`、`text.content` |
| 应用归属 | 绑定当前应用的连接。平台原始事件中带有 `robotCode` 时，解析并核对；SDK 模型未暴露的字段，用原始 payload 的解析测试覆盖 |
| 会话回复 | 保存 `sessionWebhook` 的密文和 `sessionWebhookExpiredTime`，后者按毫秒解释，转成 `route_expires_at_us`；发送前留出超时的安全余量 |
| 到期 | 保存业务结果，原因记为“会话回复授权已过期”，状态为 `reply_failed`（`route_expired`），可在记录页查看结果 |

`v0.9.1` 的公开事件模型没有定义 `robotCode`，因此应用归属校验基于实际的连接上下文和原始事件契约实现。`chatbotCorpId` 的格式与配置中 CorpId 的对应关系，在真实试点验证后记录到渠道手册。 [钉钉固定版本事件模型](https://github.com/open-dingtalk/dingtalk-stream-sdk-go/blob/v0.9.1/chatbot/model.go)

会话 Webhook 只接受可信 Stream 事件给出的平台 HTTPS 地址：校验官方允许的主机和路径，禁止重定向，固定请求方法和内容。用户输入和模型结果都不能提供该地址。发送进入终态后，按数据保留策略清理授权 URL。

### 9. 助手与主动通知

#### 9.1 助手接入

新增渠道首轮通过 `generateBotReply` 进入现有助手，复用 `openAssistantToolSession`、`botReplyMessages` 和平台工具网关。渠道适配器只负责传输，项目和用户权限仍由服务端确定。

**写策略：**

- 企微旧 Bot 的 `auto` 策略通过兼容分支读取。
- 新建 Bot 一律采用 `readonly`。
- 阶段 G 为企微新增可选的 `confirm` 策略：写草稿保存后，在 IM 中返回操作摘要和 `/bot-approve.html#draft=<id>` 链接。

**网页确认。** 要求登录，并检查绑定用户、Bot 配置、项目权限、草稿有效期和冻结参数。

- 草稿使用随机 ID。确认请求（POST）原子地把状态从 `pending` 改为 `executing`，并把草稿的执行 key 传给实际的业务写入。
- 执行中断的草稿进入待核对；用户重复点击时，返回当前的执行状态。
- 解绑、停用、删除 Bot 或撤销权限，都会使 `pending` 状态的草稿失效。
- 草稿执行复用现有的 `resolveAssistantDrafts` 和预检逻辑。网页确认相关的改动放在 `AssistantRepo` 和 `assistantHandlers`。
- 飞书、钉钉的 `confirm` 模式，在后续按同一契约验收后开放。

#### 9.2 SOP 主动通知

`notification.Service` 保留现有的投递任务、报告生成和 `lease_token`。飞书、钉钉通过 `PushSender` 发送，在只启用通知、未启用对话的配置下也能工作。

1. 在用户已绑定的可信私聊中记录目标元数据；管理页从本 Bot 已知的会话中选择目标。
2. 服务端试发成功后写入 `target_verified_at`，并绑定当时的配置版本和实际平台目标。
3. SOP 用原有的状态事件生成通知，覆盖现有枚举 `succeeded`、`failed`、`waiting` 的全部取值。
4. 发送前重新读取 Bot 和目标，保留投递记录中冻结的项目、目标和 key，按第 7 节的规则分类结果。通知的未知送达结果使用 `send_unknown`。
5. 处理节点等待通知时，复用 `waitingNodeStale` 和原有的轮次校验；节点已经推进的，取消过时通知。

**目标维护：**

- Bot 更换 Secret 后，重新验证原应用身份，目标验证状态随轮换结果一并更新。
- 切换目标时，旧的待发任务要么显式取消，要么由人工选择迁移，操作都记录下来。

**钉钉的额外限制：**

- 钉钉的通知配置，只有在独立主动发送接口真实验证成功后才能启用。
- 管理页分别展示接收连接健康、会话回复能力和主动发送权限。

**钉钉过期回复改用主动单聊补发（阶段 G）。** 前提是该 Bot 的主动单聊发送已通过真实验证，即 `target_verified_at` 有效。满足前提时，对于状态为 `reply_failed` 且原因是 `route_expired` 的钉钉私聊回复，管理员可以在记录页**显式选择**“改用主动单聊发送”。服务端在事务内重新校验以下几项：

- 操作者对该 Bot 的管理权限；
- 原发送者的绑定仍然有效，并且对项目仍有权限；
- 目标是本 Bot 已验证的、属于原发送者的单聊目标，且属于同一企业范围。

校验通过后，按人工再次发送的规则处理：`delivery_generation += 1`，生成新的发送 key；回复路由切换为主动发送，只投递已保存的结果；记录操作人、原因和路由切换。没有已验证目标时，该按钮不显示，接口返回 `409 push_target_unverified`。

#### 9.3 阶段 G 实现说明（与上文的差异）

- **目标验证记录在绑定上。** 第 5.1 节把 `target_verified_at` 放在 `bot_conversations`。实现放在 `bot_user_bindings`：飞书、钉钉的通知目标就是在本 Bot 单聊中绑定的成员（飞书 open_id、钉钉 staffId），解绑或重新绑定会清除验证，比按会话记录更直接。配置上的 `target` 只保存所选成员，展示时从绑定读取验证状态。
- **验证不绑定凭据版本。** 应用标识创建后不可修改，更换 Secret 时先校验同一应用，因此验证在轮换后继续有效，不随凭据版本失效。
- **业务写入没有幂等键。** 第 9.1 节要求把执行 key 传给业务写入；平台写入接口目前没有幂等参数。实现中执行 key 只记录在草稿上，“只执行一次”由 `pending → executing` 的加锁状态迁移保证，执行中断的草稿转为待核对、不再执行。
- **切换接收人的处理只覆盖飞书、钉钉。** 企微切换接收会话的行为保持不变，以免改变已有配置的使用方式。

**数据保留。** 暂定正文保留 90 天、终态元数据保留 180 天，可通过配置调整。每小时分批清理一次，每批 1000 条，按终态白名单和实际完成时间筛选。`running`、`ready`、`sending` 以及待核对的记录，保留到人工处置或明确的业务过期为止。

**CLI 会话日志：阶段 B 建映射表并持续写入，阶段 H 实现清理。** 同一个 Bot 逻辑会话可能对应多个消息轮次和多个原生 session，因此映射以“交互 + 请求 session”为单位保存，支持一对多。

- **启动前写入。** 在 `generateBotReply` 生成 `cliSessionID` 之后、调用 `runAssistantCLI` 启动进程之前，把 `config_id`、`project_id`、`user_id`、`conversation_id`、`bot_session_id`、`interaction_id`、`engine`、`requested_session_id` 原子写入 `bot_native_sessions`。写入失败时，本轮不启动 CLI，并在交互记录中写明追踪错误。
- **补全实际 session。** 通过已有的原生事件解析逻辑和 `runAssistantCLI` 的返回值，更新实际的 session ID；进入终态时补充完成时间。
  - 重试时恢复了同一个原生 session 的，复用原映射；实际新建了 session 的，新增一条映射。
  - 原生 session 尚未确认、或进程中断的映射，保留其追踪状态。
- **清理范围。** 保存服务端确定的存储范围和相对日志路径，按当前用户实际的 CLI HOME 解析，并验证归属。清理只处理同时满足以下条件的 Bot 原生日志：已终结、超过保留期、能由映射明确定位。逐文件记录清理结果和错误。
- **历史日志。** 升级前产生的原生日志，只为有可信记录、能精确关联的 session 生成历史映射，其余列入 `legacy_unmapped` 清单，等待人工核查。共享 HOME 下网页助手和其他来源的日志，按各自的归属处理。

阶段 B 的验证覆盖：启动前映射落库、映射写入失败、实际 session 与请求 ID 不同、同一 Bot 的多轮会话、崩溃记录。阶段 H 在临时目录构造混合来源的日志，验证只删除映射指向的到期 Bot 文件。

#### 10.1 阶段 H 实现说明（与上文的差异）

- **清理范围包含企微已有数据。** 保留规则作用于 `bot_interactions`、`notification_deliveries` 和 `bot_pending_drafts` 的全部终态记录，不区分渠道，升级后首轮清理就会处理历史企微记录。手册第 2 节第 7 步要求先确认保留设置。
- **通知记录的完成时间。** `notification_deliveries` 没有完成时间列，用“创建时间、最后一次尝试时间、发送时间都早于期限”判断，最近重试过的记录不会被提前清理。
- **每轮批次上限。** 每类每轮最多 10 批（每批 1000 条），避免升级后积压数据导致首轮长时间占用数据库。
- **飞书、钉钉开放网页确认。** 第 9.1 节原定飞书、钉钉只读；2026-11-20 按验收负责人要求，飞书、钉钉也可以选“网页确认”，以便在单聊中创建需求、派发或启动 SOP。机制与企微相同，确认链接在纯文本中单独一行；“自动执行”仍只对企微开放。
- **原生日志按文件名匹配。** 映射没有在运行时记录日志路径；清理时按请求和报告的 session ID 在该用户的 CLI HOME 中查找（CodeBuddy、Claude Code、Codex），删除后把相对路径写回 `log_path`。其他 CLI 记为 `unsupported`，留给人工核查。

| IM-06 | 发送结果未知 | 平台实际已接收而本地超时时，状态正确，并按渠道的幂等能力处理 |
| IM-07 | 只读与撤权 | 写工具被阻止；解绑和项目权限撤销对下一次工具执行生效 |
| IM-08 | 企微回归 | 旧机器人、旧绑定、群聊、流式进度、卡片与主动通知全部通过；备用发送的变化按下方专项验收 |
| IM-09 | 钉钉回复到期 | 授权过期后记录原因，已生成的结果可查看，重发按钮按路由有效期处理；阶段 G 后可显式改用主动单聊补发 |
| IM-10 | 主动通知 | 三个渠道都收到 `succeeded`、`failed`、`waiting` 通知，过时的等待通知被取消 |
| IM-11 | 人工补发 | `reply_unknown`、`reply_failed` 原子变回 `ready`，generation 加一且 key 更新；沿用已保存的业务结果，记录操作者，相同 action key 去重 |
| IM-12 | 数据升级和回退 | 旧记录可读、密钥可轮换、迁移可重入；维护窗口按“先停旧副本、再以关闭 worker 的配置启动新版本”执行；阶段 B 起新增的 CLI 会话都有映射；历史未映射清单保留；按版本与数据能力执行回退 |

**IM-08 备用发送专项**，单独保存证据：

1. 传输前已确认未发送，或平台明确拒绝且该错误允许走备用路径时：验证主动发送最多补发一次，并记录原路径和备用路径的结果。
2. 流式回复已被平台接收、但本地回执超时时：验证记录进入 `reply_unknown`，平台发送调用只计一次，页面明确提示“送达结果待核对”。
3. 在上一场景中模拟用户实际未收到：验证管理员能从记录页查看已保存的回复，并可确认或人工再次发送。再次发送使用新的 generation，并提示可能重复。
4. 发送中删除 Bot：验证 `sending → reply_unknown`，旧 worker 迟到的结果无法覆盖；项目管理员可以核对，补发操作返回 `bot_deleted`。
5. 发送中停用 Bot：验证 `sending → reply_unknown`，`ready` 状态的记录保留为暂存，重新启用后路由有效的正常发送。

**飞书窗口专项**：用可控的数据库时钟模拟以下情况——首次发送后 54 分 59 秒、55 分钟、实例重启、两个副本的本地墙钟存在偏差。检查首次发送时间不被重置；已达上限，或剩余时间不足一次请求的超时时，转为待核对。

每个平台保存一组测试企业、测试项目和普通成员的脱敏证据，记录配置版本、消息 ID、交互 ID、平台回执、实际结果和测试时间。报告使用“通过 / 失败 / 未运行 / 阻塞”四种状态。

### 12. 上线执行与交接

**上线说明与 `CHANGELOG.md` 需写明三处用户可感知的变化：**

1. **企微备用发送。** 原行为是流式失败后主动再发一次；新行为是只对确认未送达的错误执行备用发送，送达结果未知的显示“待核对”。用户可能需要到记录页查看已保存的回复，再选择人工补发。发布说明附 IM-08 专项结果、记录页入口和客服处理步骤。
2. **新建企微 Bot 默认只读。** 新建的企微 Bot 默认 `writeApproval=readonly`，不再自动执行写操作；已有企微 Bot 保持原有策略。需要写操作的项目，由管理员在 Bot 配置中显式选择（阶段 G 起可选 `confirm`）。
3. **停用 Bot 的处理。** 停用时取消正在执行的任务；已生成的回复暂存，重新启用后发送；发送中的记录进入待核对。

**试点顺序。** 依次启用：企微兼容版本 → 一个项目的飞书 → 一个项目的钉钉 → 主动通知。迁移按第 5.4 节执行，所有副本同步配置密钥和新租约协议。公开地址沿用 `AGENTFLOW_PUBLIC_URL`，确保用户能从 IM 打开绑定页和运行页。

```dotenv
AGENTFLOW_BOT_WORKERS_ENABLED=true
AGENTFLOW_BOT_MESSAGE_RETENTION_DAYS=90
AGENTFLOW_BOT_METADATA_RETENTION_DAYS=180
```
