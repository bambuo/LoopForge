## 部署

### 原生开发

`bash scripts/dev.sh` 会显式配置本地密钥，只启动本检出的 MySQL 服务，构建平台，创建 `admin` 账号，通过专门的脚本安装缺失的可观测性生成列，应用 `migrations/seed/*.sql`，并在 8090 端口启动服务。既有的目录定义由 `INSERT IGNORE` 保留不变。务必将 `.env`、`.local/` 与数据库卷置于版本控制之外。

原生安装时，API 主机需使用 Node.js 22+，并安装打算使用的 CLI。以 Codex 为例：

```bash
npm install --global @openai/codex@0.162.1
codex --version
```

在个人设置中配置 CLI 的凭据。若选择 CodeBuddy，请使用其对应的网络环境，并把其可执行文件放入 PATH 或设置 `AGENTFLOW_CODEBUDDY_BIN`。生产镜像内置 Codex、DeepSeek Harness，默认还包含 CodeBuddy。若按需安装的 CLI 缺失，对话中会显示安装操作。使用已发布镜像的 SOP 沙箱共享 Claude Code、OpenCode、Kimi Code、Pi 与 Qoder 的首次使用安装。已接入的执行机器自行管理其 CLI 安装。

企业微信通知要求平台服务的 PATH 中存在 `wecom-cli`。由本 Dockerfile 构建的平台镜像包含 `@wecom/cli@1.3.4`；已发布镜像将在下一个版本获得该组件。原生安装时，请单独执行 `npm install --global @wecom/cli@1.3.4` 安装，确保已安装系统 CA 证书，并以服务用户身份验证 `wecom-cli --version`。发送通知仍需配置企业微信机器人。

将 `AGENTFLOW_MANAGED_CLI_ROOT` 设置为可持久化的绝对目录，即可在执行运行任务的平台进程（`worker` 或 `all`）上启用每日 CLI 更新器。默认检查 Claude Code、CodeBuddy 与 Codex。将 `AGENTFLOW_MANAGED_CLIS` 设置为想更新的完整逗号分隔列表，例如 `claude-code,codebuddy,codex,pi`。其他可用的服务商 ID 为 `agy`、`cursor`、`dsh`、`kimi`、`opencode` 和 `pi`。更新器会忽略空条目，包括末尾的逗号。列表中没有名称时使用默认值，出现任何未知 ID 都会拒绝本次更新。该列表适用于定时检查、批量 CLI 更新命令，以及执行机器上的托管 CLI 更新。已有安装与回退能力保持可用。请在共享同一托管根目录的 API 进程与 worker 进程上设置相同列表。API 在解析 CodeBuddy 时使用该列表，worker 对每个根目录每天只申领一次检查。

更新器每天检查上游元数据，并在需要时下载符合条件的版本。它在运行 npm 生命周期脚本之前，使用子资源完整性（SRI）校验 npm 包完整性。Antigravity 归档文件按官方清单中的 SHA512 校验。官方 Cursor 安装器只提供带版本的 URL，不含内容校验和。Cursor 下载的完整性依赖 TLS 与匹配的强 ETag，即归档服务器给出的不透明标识。[Cursor 安装脚本](https://cursor.com/install)

Worker 需要能访问所选 CLI 的来源，必要时可配置 `HTTPS_PROXY`。更新器按服务商分别报告下载失败。

所有候选版本都要通过 24 小时观察窗口以及版本和 CLI 参数检查后才能启用。更新器会把已安装版本保留在磁盘上，以便回退和工作流固定版本，因此磁盘占用会随安装的版本增加。在启用其他服务商之前，若计划回退平台版本，请先备份托管根目录。较旧的平台版本可接受只包含原有三个服务商的清单。请把兼容的备份恢复到原来的绝对路径，以保留已记录的可执行文件路径。CLI 回退之后，自动更新会等待比被拒绝版本更新的版本。

原生执行时，平台优先使用显式的二进制覆盖配置，其次使用托管清单。平台自有的原生工作流会在其托管根目录内固定清单。接管某次运行的 worker 若以相同的绝对路径访问同一个持久托管目录，且二进制兼容，就可以复用该固定版本。拥有独立根目录的 worker 会从自己的清单解析 CLI。

更新器会在每日检查之间保留 Cursor 与 Antigravity 版本的观察记录，使每个版本即使厂商持续发布也能积累观察期。Docker 沙箱使用其镜像或沙箱安装器提供的 CLI。ZCode 使用部署提供的可执行文件。

自定义 Dockerfile 的对话工作区若没有 Node.js、npm 或 Python 3，会使用平台自带的副本。首次使用时，平台把自身的 Node.js、npm 与可重定位的 Python 复制到 `$LOOPFORGE_DATA_DIR/cli/toolchain/<build>/`，并在此后首次需要时复制每个内置 CLI（CodeBuddy、Codex、DeepSeek Harness），然后以只读方式挂载到沙箱 `PATH` 末尾。镜像自带的工具优先。只有平台架构的 glibc 镜像使用该机制；Alpine（musl）镜像需要自带 Node.js、npm 与 Python 3。新的平台构建会创建新目录并保留之前的目录：升级后请删除其他 `cli/toolchain/<build>/` 目录（每个约 200 MB，另加复制进其中的 CLI）。

用 Ctrl-C 停止前台服务，用相同命令再次启动。MySQL 数据保留在其 Compose 卷中。`docker compose stop mysql` 会停止数据库而不删除它。

使用 `AGENTFLOW_MYSQL_DSN` 对接自有 MySQL 部署。全新的账号命令或服务端连接会创建缺失的 schema 对象。既有安装的数据迁移请在审阅其前置条件后逐个执行；不要对新建数据库盲目重放全部历史迁移。

### 选择执行器

- 需求澄清、Bot 回复、SOP 通知报告、运行评估与定时 AI 任务的模型选择器可接受受支持 CLI 的模型。API 客户端可发送 `codex:<model>`、`claude-code:<model>` 或其他带 CLI 前缀的模型 ID。旧式裸模型 ID 仍按 CodeBuddy 的 ID 处理。省略模型或只写 `default` 时，优先使用执行账号的个人默认模型。在回退顺序中，既有的 CodeBuddy 默认值优先。具体模型会原样传给对应的 CLI。
- 在**个人配置**中，为每个仓库主机添加 Git 凭据，并为使用的每个 CLI 添加执行器凭据。Git 按仓库协议、主机与端口选择凭据。第一个配置的执行器会成为个人默认执行器。你可以修改它，并选择默认模型、推理强度与对话审批模式。CodeBuddy 除网络环境外还接受可选的 Base URL。URL 留空则使用该环境的官方端点。在远程执行机器上使用自定义 CodeBuddy URL 需要 Runner 0.11.2 或更高版本。
- 澄清使用指派人的凭据，未指派时回退到项目所有者。Bot 回复使用绑定的发送者，报告使用该运行的责任账号，评估使用发起请求的账号。辅助审批使用本轮轮次的 CLI 与选定模型。
- SOP 角色与静态预览可各自选择 CLI。新建角色与静态预览的默认值仍是 CodeBuddy。要在内置模板中使用其他 CLI，请把它复制到项目中并更新其角色，或以平台管理员身份编辑该模板。
- 在平台上设置 `AGENTFLOW_BASELINE_ALIGN_EXECUTOR=codex`，可用 Codex 运行定时的基线冲突消解器。该设置接受内置执行器 ID，包括代表 Claude Code 的 `claude`。该设置为空时，消解器默认使用 CodeBuddy。新运行会在其快照中记录所配置的执行器。
- 要从源码构建中省略 CodeBuddy，请向 Docker 传入 `--build-arg CODEBUDDY_PACKAGE=`，或在开发用 Compose 构建命令前加 `CODEBUDDY_PACKAGE=`。将该镜像用作平台沙箱的 `AGENTFLOW_ISOLATED_IMAGE`。若没有共享镜像，请为内置回退 Dockerfile 设置 `AGENTFLOW_SKIP_CODEBUDDY_INSTALL=1`。自定义 Dockerfile 自行管理所需软件包。启用该开关后，默认托管 CLI 列表也会省略 CodeBuddy。请设置 `AGENTFLOW_MANAGED_CLIS` 以管理显式的服务商列表。
- 缺陷跟踪系统 MCP 认证使用目录中显式的请求头或部署的 `AGENTFLOW_MCP_TOKEN`。项目范围的跟踪系统使用各自的 MCP 授权请求头。
- 将 `AGENTFLOW_GONGFENG_HOST` 设置为受管 Git 主机（主机名与可选的 HTTPS 端口），以启用其仓库与合并请求链接及令牌检查。工蜂 OAuth 还需要其应用凭据与回调地址。既有的 OAuth 端点覆盖配置仍然优先。
- 需要时，将 `AGENTFLOW_TAPD_HOST` 设置为部署专属的 TAPD Web 主机。生成的 TAPD 工作项链接默认使用 `www.tapd.cn`。

### 容器安装

```bash
./start.sh                        # install or start in the background (same as bash scripts/install.sh)
./start.sh logs                   # follow platform logs
./start.sh stop                   # stop; ./start.sh down removes containers but keeps data volumes
./start.sh restart                # restart the platform container
./start.sh pull                   # refresh images; times ghcr.io against ghcr.nju.edu.cn
MIRROR=ghcr.io ./start.sh         # install from ghcr.io without the speed test
MIRROR=ghcr.nju.edu.cn ./start.sh # force that host instead of the speed test
./start.sh dev                    # build this checkout instead (compose.dev.yaml)
./start.sh release                # switch a source build back to the published image
```

安装器会检查 Docker、Compose、Python 3 与 curl。它会在 Linux 上使用 apt、dnf 或 yum（macOS 上使用 Homebrew）安装缺失的 Python/curl 软件包，使用官方安装脚本安装 Docker，并使用带 SHA-256 校验的固定官方版本安装缺失的 Linux x86_64/arm64 Compose 插件。插件会为当前 Docker 用户安装，Docker 需要 sudo 时则全局安装。macOS 的 Compose 来自 Docker Desktop。设置 `LOOPFORGE_YES=1` 可自动接受安装提示；但仍然需要联网以及包管理器/管理员权限。安装器会生成带唯一密钥的 `.env`，拉取并启动容器，安装可观测性列并应用 `migrations/seed/*.sql`。可以安全地重复执行。若默认端口已被占用，请在首次运行前于环境中设置 `AGENTFLOW_HTTP_PORT` 或 `LOOPFORGE_MYSQL_PORT`（也可以稍后编辑 `.env`）。

请以安装所有者身份运行，普通 Linux 用户亦可。若该用户无法直接访问 Docker，安装器会校验 sudo，并一致地使用 `sudo -n docker` 执行 Compose、schema 安装与 seed。每次操作前它都会检查 sudo 凭据是否在长时间构建中过期，在终端中会重新提示，在无人值守模式下则直接失败并给出说明。它不要求把用户加入 Docker 组，也不要求重新登录。无人值守安装请先执行 `sudo -v`；`LOOPFORGE_YES=1` 只接受安装提示，不会绕过操作系统权限。既无 sudo 也无 Docker 访问权限时会立即失败并给出说明。无根 Docker 使用其当前上下文的 Unix socket；远程 Docker 上下文需要另行配置部署，因为沙箱工作区是本地绑定挂载。

`compose.yaml` 是已发布镜像的堆栈，从不执行构建：`./start.sh`、`scripts/install.sh` 与直接执行 `docker compose --profile platform up` 都会拉取其中固定的 GHCR 发布版本（当前为 `ghcr.io/tencent/loopforge:0.4.2`）。该固定版本与检出中的迁移和 seed 相匹配，因此安装时请检出一个发布标签。只有需要覆盖时才设置 `LOOPFORGE_IMAGE`（例如设为 `@sha256:` 摘要）；保存在 `.env` 中的值优先于之后固定版本的变更。

升级时，先更新检出，应用所需的升级迁移，然后刷新容器。沙箱目录的升级请参考[将既有沙箱迁移到内联资产](#将既有沙箱迁移到内联资产)。

```bash
git fetch --tags && git checkout vX.Y.Z
./start.sh pull
```

新的 `compose.yaml` 会一并带来镜像固定版本与新的平台设置，只要其中任一发生变化，`./start.sh pull` 就会重建平台容器。由 `./start.sh dev` 产生的源码构建不会被 `./start.sh pull` 重建；更新检出后需再次运行 `./start.sh dev`。只运行 `./start.sh pull` 会保留固定的版本。若 `.env` 中保存了 `LOOPFORGE_IMAGE`，也要把它改成检出对应的发布版本；用较新的镜像搭配较旧的 `compose.yaml` 可能缺少该版本需要的设置。

在 `ghcr.io` 下载缓慢的环境中，`./start.sh` 与 `./start.sh pull` 会把 `ghcr.io` 与 [ghcr.nju.edu.cn](https://doc.nju.edu.cn/books/e1654/page/ghcr) 做速度对比。只有在南京镜像的清单摘要与刚从 ghcr.io 读取的摘要一致时才会使用它；实际拉取的是该摘要，随后再打回 `compose.yaml` 中的名称，`compose.yaml` 信任该主机。官方摘要缺失、摘要不一致或镜像站拉取失败时，仍使用 `ghcr.io`。`MIRROR=ghcr.io` 强制使用上游镜像仓库；配置任何其他 `MIRROR` 主机则强制使用该仓库，跳过速度测试，且不回退。该选择不会写入 `.env`。安装时的拉取策略仍为 `missing`，因此会保留本地镜像且不再测速；`./start.sh pull` 会对各仓库测速并从胜出者刷新。GitHub Release 会记录镜像摘要；执行 `docker image inspect --format '{{index .RepoDigests 0}}' ghcr.io/tencent/loopforge:<pin>` 后，`@` 之后的摘要应与之一致。Docker 的 `registry-mirrors` 设置（包括 `https://docker.nju.edu.cn`）只对 Docker Hub 生效，不能用作 `MIRROR`。若 `LOOPFORGE_IMAGE` 的值不是 `ghcr.io` 的 `名称:标签` 形式，则保持原样不作改动。

```bash
./start.sh
MIRROR=ghcr.io ./start.sh pull
MIRROR=ghcr.nju.edu.cn ./start.sh pull
```

`./start.sh dev`（或 `LOOPFORGE_BUILD_FROM_SOURCE=1 bash scripts/install.sh`）会依据 `compose.dev.yaml` 把本检出构建为 `loopforge-platform:local`。它会把 `COMPOSE_FILE=compose.yaml:compose.dev.yaml` 写入 `.env`，因此之后的运行和直接使用的 `docker compose` 命令都会继续使用源码构建，直到执行 `./start.sh release`。源码构建会复用 npm、Go 模块与 Go 编译器缓存。

在 `main` 上推送 `vX.Y.Z` 标签后，一旦 `platform` 工作流在该提交上通过，就会运行 `release` 工作流。带标签的 `compose.yaml` 必须已固定 `loopforge:X.Y.Z`。该工作流把 `ghcr.io/<owner>/loopforge` 发布为 `X.Y.Z`、`X.Y`、`latest` 与 `sha-<commit>`，用 `./start.sh` 对推送的摘要做冒烟测试，并创建 GitHub Release。复刻仓库以自己的所有者名义发布；分发镜像前请为团队设置 GHCR 软件包的可见性/访问权限。默认只在镜像缺失时才拉取；请使用不可变标签/摘要，或在更新可变标签时设置 `LOOPFORGE_PULL_POLICY=always`。既有 `.env` 值优先；更新安装时请在其中修改已保存的镜像或 URL。Compose 会以有上限的超时等待 API 健康检查通过，然后才安装 schema 扩展与 seed。

打开平台并在浏览器中创建第一个账号；该账号会获得平台管理权限。在该账号存在之前，登录页只提供这一步设置。

初始设置期间，请把云安全组或防火墙限制为运维人员的 IP。在管理员账号创建之前，不要把首个账号设置页暴露给任意互联网客户端。

平台监听 `LOOPFORGE_BIND`，默认 `0.0.0.0`，不会提示输入访问 URL。安装器会打印公网、局域网与本地地址；在腾讯云、阿里云、AWS、GCP 与 Azure 上，它会从服务商的链路本地元数据服务读取公网 IP，其他位于 NAT 之后的环境需自行填写公网 IP。`LOOPFORGE_PUBLIC_URL` 是可选项，只改变打印出的地址。请在云安全组/防火墙中放行 HTTP 端口，或使用 HTTPS 反向代理。既有 `.env` 文件会被保留；没有绑定设置的旧安装现在也监听 `0.0.0.0`。仅本地使用的安装可设置 `LOOPFORGE_BIND=127.0.0.1`。请代理 WebSocket 与流式请求。HTTPS 在代理处终止时设置 `AGENTFLOW_SECURE_COOKIES=true`。请保证 `AGENTFLOW_SESSION_SECRET` 在各 API 实例与重启之间保持稳定。

企业认证网关可通过 `AGENTFLOW_TRUST_IDENTITY_HEADERS=true` 以请求头方式登录用户。该选项默认关闭。此时 API 只接受来自回环对端的 `Staffname` / `x-staff-name`，且仅当它能判断请求来自网关时：

- 将 `AGENTFLOW_IDENTITY_HEADER_SECRET` 设置为随机值，并让网关通过 `X-AgentFlow-Gateway-Secret` 发送它。网关必须覆盖（而不是透传）客户端的 `Staffname`、`Staffid`、`x-staff-name` 与 `X-AgentFlow-Gateway-Secret` 请求头。
- 未配置密钥时，任何携带 `X-Forwarded-For`、`Forwarded` 或 `X-Real-IP` 的请求都被视为经转发的客户端，其身份请求头会被忽略。这只保护会添加这些请求头之一的代理：同主机上透传客户端请求头但不添加它们的代理（例如未设置 `proxy_set_header X-Forwarded-For` 的 nginx `proxy_pass`），以及主机上的任何其他进程，仍可冒充任意用户登录。只要启用了请求头登录就应设置该密钥；缺失时平台会在启动时记录警告。

#### Docker 沙箱

即使目录 SQL 尚未安装，平台也会暴露一个内置的默认沙箱（`generic-docker`，由其自带 Dockerfile 构建）。它是内存中的回退方案，不会向数据库插入记录。已保存的 `generic-docker` 配置优先生效，包括其配置的驱动与环境。默认沙箱不可删除；如需改变任务运行方式，请编辑其配置或另建配置。未选择沙箱的 SOP 在该沙箱中运行。完整安装器仍会导入初始 SOP 与欢迎项目；seed 的 `generic-docker` Dockerfile 与平台镜像一致，因此 Compose 沙箱会复用 `AGENTFLOW_ISOLATED_IMAGE` 而不执行构建。未安装目录 SQL 时，首次运行会构建一次内置 Dockerfile。

`native` 沙箱使用执行机器的工具链与已配置的环境变量。对于 native SOP 检出，宿主机使用检出所用的 Git 凭据刷新按仓库隔离的私有缓存，并把对象复制进每个工作树。Docker 沙箱直接从远端克隆。Compose 平台镜像不含 bwrap，因此 native 工作需在执行机器或原生安装的平台上运行。详见[对话工作区](06-对话工作区与原生CLI.md#仓库缓存)。迁移 `041_native_sandbox_inline_assets.sql` 会把 local 配置转换为 native，保留普通环境变量，并把依赖旧默认值的 SOP 迁移到 `generic-docker`。

对于以普通宿主机用户身份运行的 native 服务，默认/root Docker 镜像会以该服务用户的 UID/GID 运行，以便私有工作区在不放宽权限、不增加能力的前提下保持可访问。显式选择非 root 用户的镜像会保留该身份；运维人员须为这些镜像安排兼容的绑定挂载属主。

Compose 部署会把宿主机 Docker socket 挂载进平台容器，使内置 AI SOP 开箱即用。`AGENTFLOW_ISOLATED_IMAGE` 指向已安装的平台镜像：默认沙箱会从同一镜像启动独立的兄弟容器，无需二次下载 CLI 或构建镜像。它们不挂载 Docker socket。自定义 Dockerfile 仍会构建并缓存各自的镜像。运行工作区挂载在 Compose 网络的 `/workspace`。由于绑定挂载由宿主机 Docker 守护进程解析，`LOOPFORGE_DATA_DIR`（由 `scripts/configure.sh` 写入 `.env`，默认 `./.data`）会以相同绝对路径挂载进平台容器；工作区与 CLI 状态都位于其下。native 对话工作区以同样方式绑定挂载其会话根目录，因此 `compose.yaml` 把 `AGENTFLOW_CONVERSATION_DIR` 设为 `${LOOPFORGE_DATA_DIR}/conversations`。Compose 部署中的对话工作区使用 Docker 沙箱：native（bwrap）沙箱需要用户与 PID 命名空间，非特权平台容器无法创建，且镜像不提供 bubblewrap。native 沙箱请使用原生安装或已接入的执行机器。附件与其他按用户保存的助手状态保留在 `AGENTFLOW_ASSISTANT_SESSION_DIR`（`platform-data` 卷中的 `/data/assistant`），该目录从不挂载进工作区。未设置 `AGENTFLOW_CONVERSATION_DIR` 的平台容器也会把会话根目录放在那里，此时打开对话工作区会以 `mkdirat ... read-only file system` 失败。

使用标准 CLI 执行器的 Docker SOP 节点会先在沙箱用户的 PATH 中查找 CLI。缺失时，LoopForge 会在有共享安装的情况下使用平台镜像的共享安装，或在容器中运行与对话工作区相同的安装器。安装使用沙箱配置的代理，该容器中后续节点会复用该 CLI。容器内安装需要可写文件系统与官方软件源访问能力。只读沙箱可使用镜像中或挂载工具链里的 CLI。ZCode 使用镜像提供的官方可执行文件。

访问 Docker socket 等同于拥有宿主机 root 权限。由此有两条防护措施：不存在未隔离的沙箱类型，因此平台自行运行的每个任务都在沙箱中（`AGENTFLOW_LOCAL_SANDBOX` 设置已移除）；且只有平台管理员才能把仓库指向宿主机源路径。即便如此，任何能运行 SOP 的人都能在本机容器中执行代码，因此只应把账号授予信任的人，并不要把服务暴露到不受信任的网络。Agent CLI 还会按其原生规则应用所绑定仓库自身的配置，包括无人值守的 SOP 运行：`AGENTS.md`/`CLAUDE.md` 指令、`.codebuddy/`、`.claude/settings.json`（钩子与环境）与 `.mcp.json` 都可在沙箱内启动命令或 MCP 服务器。只绑定你信任其内容的仓库。要不使用 socket 运行，请从 `compose.yaml` 中移除 `docker.sock` 卷，然后为 SOP（包括现在运行于 `generic-docker` 的欢迎 SOP）连接独立的具备 Docker 能力的 worker 或执行机器。

#### 慢速网络：克隆与镜像构建限制

克隆仓库与构建自定义沙箱镜像时会从工作进展中报告进度，其错误会保留 Git 或 Docker 输出的最后几行。对话会显示平台与已接入执行机器上当前的 Docker 构建步骤。耗时较长且无输出的 Dockerfile 步骤会一直执行，直到其调用方或已配置的限制停止构建。所有设置都接受 Go 时长格式，例如 `90s` 或 `20m`。`0` 表示关闭该限制。请在运行该命令的平台进程或执行机器上设置这些变量。

执行机器的对话工作区准备遵循对话请求的生命周期。停止本轮或断开执行机器的控制连接都会取消准备。

| 设置 | 默认值 | 适用范围 |
|---|---|---|
| `AGENTFLOW_GIT_CLONE_STALL_TIMEOUT` | `5m` | 无输出的 `git clone`。平台从仓库本地源路径克隆时不适用，因为其最后的重新打包过程无输出。 |
| `AGENTFLOW_GIT_CLONE_TIMEOUT` | 平台上关闭，执行机器上为 `10m` | 整个 `git clone`。执行机器默认沿用原先固定的 10 分钟限制。 |
| `AGENTFLOW_DOCKER_BUILD_STALL_TIMEOUT` | 关闭 | `docker build` 可选的无输出限制。静默的 `RUN` 步骤也算作无输出。 |
| `AGENTFLOW_DOCKER_BUILD_TIMEOUT` | 关闭 | 整个 `docker build`。 |

以这种方式被中止的克隆不会重试，因为重试仍会等待同一网络。当执行主机访问 GitHub 或 Debian 镜像站缓慢时，请让 git 走代理（`git config --global http.proxy`），并在 Dockerfile 中使用就近的软件包镜像站，而不是提高这些限制。

#### 通过 HTTPS 访问自建 Git 仓库

在**平台管理 → Git 主机信任**中添加 HTTPS 主机，若端口不是 443 需一并填写。解析主机名或手动输入已批准的 IP 地址，然后审阅并确认该列表。对于 IPv4 服务器，在主机字段中输入其主机名，并在授权中包含其 IPv4 地址。直连 IPv6 时，端口 443 输入 `fd00::2`，自定义端口则输入 `[fd00::2]:8443`。授权覆盖该 IP，且 Git 服务器的 TLS 证书必须在其使用者可选名称中包含该 IP。克隆 URL 使用带方括号的形式，例如 `https://[fd00::2]:8443/team/repo.git`。

已登录用户可在**个人设置 → Git 访问令牌**中看到该实例的主机名或 IPv6 地址以及 Git 服务商。他们可以选择该实例并输入自己的令牌。已批准的 IP 地址列表会显示在平台管理中。当 GitLab 返回的合并请求链接使用不同主机或端口时，LoopForge 会用其已查询过的授权端点来跟踪该 MR。

平台在进行令牌校验、拉取或合并请求发现以及状态同步的连接拨号前，会检查已批准的地址。HTTPS 连接使用平台常规的 TLS 信任链。对于每个已登记的主机名与端口，平台只拨号该授权中的地址。`AGENTFLOW_GIT_EGRESS_ALLOW_CIDRS` 仅适用于没有 HTTPS 授权的主机。

将主机从部署 CIDR 迁移过来时，请把平台应能访问的每个 IP 都包含进授权。要轮换地址，请编辑已保存的列表，并在确认前审阅新增与移除的地址。

#### 通过 SSH 访问 Git 仓库

对于 GitLab.com、自建 GitLab、Gitea、Gogs、GitHub 以及其他提供该传输方式的 Git 主机，可使用 Git SSH。在**项目设置 → 代码仓库**或**快捷入口**中，输入克隆地址，例如 `git@gitlab.com:group/repo.git` 或 `ssh://git@git.example.org:2222/group/repo.git`，并选择已有的默认分支。GitHub 的 HTTPS 仍使用 GitHub 授权或 PAT。

1. GitHub（`github.com:22` 与 `ssh.github.com:443`）使用内置主机公钥。对于其他主机，由平台管理员打开**平台管理 → Git 主机信任**，输入主机名与可选端口，并选择**读取公钥并审阅指纹**。平台通过受 `AGENTFLOW_GIT_EGRESS_ALLOW_CIDRS` 约束的 SSH 握手读取公钥。对于私有主机，请选择一台可访问该服务器且支持主机公钥发现的在线个人执行机器。也可以手动输入 OpenSSH 公钥，包括为一台主机输入多个公钥。确认前请把显示的 SHA256 指纹与 Git 服务商或服务器管理员核对。该登记对整个平台生效，范围为该确切主机与端口。编辑与移除会在下一次由平台管理的 Git 操作或新启动的工作区 CLI 与终端会话中生效。
2. **0.11.1** 及更高版本的执行机器在任务或工作区请求需要 Git SSH 时会收到匹配的平台条目。部署也可以把 `AGENTFLOW_GIT_SSH_KNOWN_HOSTS` 指向专用的 OpenSSH `known_hosts` 文件。Compose 部署请把该文件放在 `LOOPFORGE_DATA_DIR` 绑定挂载之下，并在 `.env` 中设置其绝对路径。平台文件与页面记录的条目会合并生效。文件中请使用确切的主机名或 IP 地址，非默认端口写作 `[host]:port`。同一主机与端口下，平台下发的受信公钥优先。当平台仅下发吊销记录或对该端点没有条目时，执行机器本地公钥生效。两处的显式 `@revoked` 条目都会生效。编码后的条目每次派发允许 1 MiB。**0.9.3** 至 **0.11.0** 的执行机器仍需自备文件与变量。独立部署的 worker 可从共享数据库读取注册表，或使用自己的部署文件。

   若数据库注册表不可用，平台会记录错误并继续使用部署文件与内置的 GitHub 公钥。按相同的优先级规则，执行机器本地公钥仍然可用。已配置但无法读取的 `known_hosts` 文件仍会阻止 Git SSH 操作，因为它可能包含吊销记录。管理列表会把无效条目标记为待移除，主机名有效的条目可以就地修复。无效条目不贡献任何受信公钥。

   请在执行机器与自定义沙箱镜像中安装 Git 与 OpenSSH 客户端。Docker 沙箱命令需要沙箱与执行进程共享 Linux 内核以使用签名代理 socket。若 Docker 虚拟机与 native 执行机器分开，请使用托管检出与交付，或为交互式 Git 命令使用 native 沙箱。
3. 为无人值守执行生成不带口令的专用 SSH 密钥。把每个公钥添加到你的托管账号，并授予其访问所需仓库的权限。若运行需要推送，请授予写权限。在**个人设置 → Git SSH 密钥**中，为每个 SSH 主机添加一个私钥，例如 `gitlab.com` 或 `git.example.org:2222`。省略端口表示 22。编辑该主机的条目即可替换其密钥。

仓库会自动使用当前用户对应其 SSH 主机与端口的密钥；同一主机与端口上的仓库共用该密钥。仅当该主机没有个人密钥时，仓库表单才会显示红色警告。该提醒不会阻止保存仓库或完成设置；凭据与主机信任可以在首次 Git 操作之前配置。不存在仓库专属或默认回退密钥。检出与 SOP 执行使用责任用户的密钥。对话提交与工作区终端使用发起请求用户的密钥。临时签名代理会在命令或终端结束时关闭。终端的代理绝不驻留在共享工作区中：使用 `bwrap` 驱动时，它位于仅绑定进该终端的私有目录；使用 `local` 驱动（无隔离）时，它位于工作区之外权限为 0700 的目录。Docker 与 seatbelt 工作区的所有进程共享同一文件系统视图，因此其终端不获得个人 SSH 密钥；请在那里使用平台的提交操作进行推送。除非显式指定 `provider` 为 `ssh`，`git@github.com:` 与 `ssh://git@github.com/` 地址会被保存为 GitHub 仓库（HTTPS + 令牌，自动创建合并请求）。要轮换密钥，请在设置中替换它，并在主机侧吊销旧公钥。

SSH 负责克隆、拉取与推送。对话交付会返回分支与提交 SHA。你可以选择性地添加仓库的 Web URL，以便打开主机并手动创建 PR/MR。需求导入与 PR/MR 自动化需要托管平台的 API 凭据。要自动化这些操作，请在**设置 → 资产 → MCP** 中添加对应托管平台的 MCP，为它分配独立的受限令牌，并挂载到相关的 Agent 或工作流。[CNB 不支持 Git SSH](https://docs.cnb.cool/en/guide/git-access.html)；它使用 HTTPS 加 CNB 访问令牌，不在本集成范围内。

### 聊天机器人（企业微信、飞书、钉钉）

聊天机器人在 Bot 页面按项目配置。部署需要提供：

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `AGENTFLOW_CREDENTIAL_KEYS` | 由 `scripts/configure.sh` 生成 | `kid:base64(32 字节)[,…]`；第一个密钥用于加密新的 Bot 密钥。每个副本都需要相同的值。请与数据库一并备份：缺失该值将无法解密已保存的密钥。 |
| `AGENTFLOW_PUBLIC_URL` | `LOOPFORGE_PUBLIC_URL` | 聊天用户用于账号绑定、运行页面与企业微信写确认的地址。必须能从其浏览器访问。 |
| `AGENTFLOW_BOT_WORKERS_ENABLED` | `true` | 在升级窗口设为 `false`：不建立接收连接，不投递通知，Bot 配置写入返回 `503 bot_maintenance`。 |
| `AGENTFLOW_BOT_BODY_RETENTION_DAYS` | `90` | 对话轮次、通知或写入草稿完成后，其文本与该轮次的原生 CLI 日志被移除前的天数。`0` 表示保留。 |
| `AGENTFLOW_BOT_RECORD_RETENTION_DAYS` | `180` | 已完成记录本身被删除前的天数。`0` 表示保留；低于正文保留天数的值会被提升到该天数。 |

保留期清理在运行 Bot worker 的每个进程中每小时执行一次，且从不触碰仍在等待某人处理的记录（进行中、待发送或投递状态未知）。Bot 轮次的原生 CLI 日志位于 `AGENTFLOW_ASSISTANT_SESSION_DIR` 下的 CLI home 中；存在多个 API 副本时该目录必须共享，否则未运行某轮次的副本会把该日志记为缺失。渠道配置、升级与回滚步骤见[企业 IM 手册](08-渠道Bot与通知.md)（中文）。

### 账号

在浏览器中创建的第一个账号会成为平台管理员。此后，只要 `AGENTFLOW_ALLOW_SIGNUP` 为 `true`（默认值），任何能访问登录页的人都可以注册为普通用户。已注册用户可以在你的 worker 上创建需求并运行 SOP，因此对于任何可从不受信任网络访问的安装，请设置 `AGENTFLOW_ALLOW_SIGNUP=false`，改为显式创建账号。

平台管理员在**平台管理 → 成员账号**（Platform administration → Member accounts）中创建账号：输入登录名与初始密码，可选择授予管理权限，然后把密码交给同事。同一页面会列出所有账号，并可重置密码账号的密码；通过 GitHub 或网关登录的账号无法在此设置密码。新账号会加入欢迎项目，与自助注册相同。

LoopForge 假定团队之间相互信任。每个已登录账号都能列出所有项目、需求与运行。项目设置与仓库只能由项目所有者或平台管理员修改，个人凭据只能由其所有者修改。不要用一套安装来隔离互不信任的租户。

没有浏览器时，导出原生安装的 `.env` 值并运行显式账号命令：

```bash
set -a; source .env; set +a
read -r -s -p 'Password: ' account_password; echo
printf '%s\n' "$account_password" | go run ./cmd/loopforge-account -user alice
unset account_password
```

仅在授予平台管理权限时使用 `-admin`。再次运行该命令会轮换该账号的密码。密码哈希使用 bcrypt。浏览器会话使用签名的 HttpOnly、SameSite Cookie，七天后过期。没有具名个人会获得隐式管理员角色；其他管理员可通过现有平台管理界面管理。

### Worker 与执行机器

上游进程角色仍为 `-role api`、`-role worker` 与 `-role all`。API 与 worker 实例必须共享 MySQL 数据库，并使用适合各自部署的配置。分离控制面与执行面时，请设置 `AGENTFLOW_CONTROL_TOKEN`、`AGENTFLOW_CONTROL_URL` 与 `AGENTFLOW_WORKER_URL`。请把 `AGENTFLOW_PLATFORM_MCP_URL` 设置为执行容器可访问的实际平台 URL。

个人执行机器通过执行机器页面上的短期绑定码接入。安装脚本位于 `/runners/install.sh`。`AGENTFLOW_RUNNER_BINARY` 可指向支持 `{os}` 与 `{arch}` 替换的二进制。容器镜像内置 Linux/macOS 的 amd64/arm64 执行机器与门禁二进制。原生源码安装可按需用 Go 构建。

macOS 上的 Docker 工作区使用 Linux 执行机器可执行文件处理 Git 凭据与 MCP 调用。安装器会选择已安装 macOS 执行机器的架构，包括在 Rosetta 下运行的 Intel 二进制。对于 Apple Silicon 上的通用执行机器，它会安装 arm64 辅助程序，并在可用时追加 amd64 辅助程序。前台启动与 `--no-start` 打印的命令都选择原生 arm64 切片，包括从 Rosetta shell 启动的情况。在 Intel Mac 上，安装器会安装 amd64 辅助程序。默认情况下，它把辅助程序放在宿主二进制旁边。执行机器侧的 `AGENTFLOW_RUNNER_BINARY` 模板若带 `{os}`，会决定安装与运行时路径。要同时安装两个辅助程序，请使用 `{arch}` 并为每个架构指定不同的目标位置。安装器会保存该模板以供升级使用，并把它写入 launchd 和 `--no-start` 打印的启动命令。辅助程序路径必须解析为与 macOS 执行机器不同的文件。

安装器会把辅助程序目标位置与已暂存的 macOS 二进制核对，并在替换已安装的执行机器之前安装所需的 Gate MCP 辅助程序。若现有执行机器已有可用的 Docker 辅助程序，升级时需要在替换二进制并重启服务之前，于新执行机器配置的路径上准备兼容的辅助程序。已安装 launchd 配置中的相对模板使用该任务的工作目录。安装器与更新器在替换 Linux 可执行文件前会校验其格式、架构与加载段。自定义安装会保留兼容的现有辅助程序。从本地检出构建的执行机器可以用该检出构建其配套程序。带 `{os}` 占位符的下载 URL 可作为执行机器的下载源同时提供两个二进制。

启用平台更新后，macOS 执行机器会在启动时于后台同步辅助程序。版本检查失败会在重新扫描期间重试，包括旧辅助程序仍然可用的情况。同步进行期间，可读且兼容的本地 ELF 或本地配置的脚本包装器可以带可执行权限复制进 Docker 工作区。需要 Git 或 MCP 辅助程序而当前缺失的操作最多等待五秒以完成初始同步。后台下载会在自身的传输超时内继续。

平台管理员可在**平台管理 → 平台共享 CodeBuddy Key**（Platform administration → Shared CodeBuddy Key）中共享一个 CodeBuddy API Key：选择签发它的网络环境以及成员可使用的模型（第一个为默认）。没有自备密钥的成员随后用它聊天并运行 SOP，且限于这些模型；配置了其他模型的身份会改在默认模型上运行，运行记录也会说明这一点。自备密钥的成员仍可用自己的密钥搭配任意模型。澄清、报告、Bot 与运行评估使用相关账号的个人凭据。定时提示词遵循所选 CLI 的凭据与赞助设置。该密钥与个人密钥一样存储在数据库中，保存后不再显示。`AGENTFLOW_ASSISTANT_SPONSOR_LOGIN` 曾借用某个账号的密钥且限于 `deepseek-v4.1-flash`，在未配置共享密钥时仍然生效。

请在平台 UI 中配置服务商凭据，而不是宿主机全局 CLI 配置。凭据由上游运行时绑定到责任执行者。首页编辑器与 SOP 角色各自独立选择内置 CLI。在首页模型选择器旁选择执行器；其 API Key（以及可选的 Codex/Claude Base URL）来自你的个人设置。切换执行器会保留草稿；已保存的对话会记录所用执行器。主 Bot 的写入仍会经过平台工具网关及其审批检查。定时助手任务可选择任意受支持的 CLI，并作为普通对话轮次运行；Codex 与 Claude Code 仍需要该账号自有的凭据。实时模型测试需显式开启；只有需要加载本地凭据的验收套件才设置 `AGENTFLOW_LIVE_TESTS=1`。

### GitHub 凭据

用户可在个人凭据中或添加仓库时选择 **连接 GitHub**，复制显示的 PIN，并在 GitHub 上批准。平台会把该授权保存到该已登录用户既有的 Git 凭据槽位。仓库选择器会列出该账号拥有、与其共享或可通过其组织访问的仓库，支持对已加载仓库分页与搜索，并把所选仓库真实的默认分支填入表单。仍可手动输入 PAT。

全新安装使用内置的 LoopForge OAuth 应用。用户无需创建应用、配置 Client ID 或申请 PAT：选择 **连接 GitHub**，复制 PIN 并在 GitHub 上批准 LoopForge 应用即可。GitHub 的确认步骤无法绕过；设备授权不是零交互登录。

应用配置属于部署事项，不在个人凭据中显示。需要自有应用的运维人员可注册 OAuth 应用，启用 **Device Flow**，在支持刷新之前保持令牌不过期，并在 `.env` 中用 `AGENTFLOW_GITHUB_CLIENT_ID` 设置其公开 Client ID。无需 client secret。部署环境覆盖内置应用以及任何数据库覆盖。仅管理员可用的 `PUT /api/auth/github/config` 端点仍可用于显式的数据库覆盖；空的 Client ID 会显式禁用设备授权，而不是静默恢复默认值。既有的显式配置会被保留。

该流程请求 OAuth 的 `repo` 范围，以便私有克隆、推送、Issue 与 PR 操作可用。GitHub 的 OAuth 范围覆盖可访问的仓库；在 LoopForge 中选择某个仓库会把它绑定到项目，但不会收窄 OAuth 授权。组织 SSO 或第三方应用限制可能需要组织批准。参见 [GitHub 的设备授权文档](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow)。待处理的授权会过期且仅保存在 API 内存中：多个 API 实例部署时请为 `/api/auth/github/*` 使用会话保持，且 API 重启后需重新发起授权。令牌与 GitHub 设备码绝不会发送到浏览器。

GitHub Issue 导入与 PR 状态同步使用项目所有者的 Git 令牌。Git 操作与可选的 GitHub MCP 集成使用责任用户的令牌。公开读取可能无需令牌；私有仓库与写入需要仓库访问权限。GitHub MCP 必须显式安装，且只会把凭据发送到其官方 HTTPS 端点。

平台创建的 Git 提交使用责任本地账号名称，以及不可投递的 `@users.noreply.loopforge.invalid` 邮箱。本地账号并不代表建立了企业邮箱或已验证的 GitHub 身份。

#### 迁移既有 GitHub 凭据

从 v0.4.0 升级到按主机读取 HTTPS 凭据的版本时，请停止旧的 API 与 worker 并保持 MySQL 运行。在启动升级后的平台或运行 `./start.sh pull` 之前，手动应用目标版本的 `036_git_http_credentials.sql`。Compose 部署请使用：

### CodeBuddy 认证环境

在个人设置中选择该 API Key 所属的网络环境；「获取 API Key」链接会打开该版本的密钥页面。某个版本的密钥发往另一版本时返回 HTTP 401，来自第三方模型服务商（DeepSeek、OpenAI 等）的密钥不是 CodeBuddy 密钥。该设置按用户生效；公开安装不会假定企业环境。

| 版本 | 存储值 | 密钥页面 |
| --- | --- | --- |
| 国际版 | 空 | https://www.codebuddy.ai/profile/keys |
| 中国版 | `internal` | https://copilot.tencent.com/profile/ |
| iOA | `ioa` | https://tencent.sso.copilot.tencent.com/profile/keys |

### 隔离容器验收

运行 `python3 scripts/test-install.py -v` 执行安装器回归测试，覆盖 sudo 选择、直接访问 Docker、无人值守权限失败、重复安装、镜像模式与访问 URL。使用本地构建的平台镜像时，`LOOPFORGE_INSTALL_TEST_IMAGE=your-image bash scripts/test-install-live.sh` 会在随机端口上的隔离 Compose 项目中验证真实的 root 与 UID 65534 安装、非回环 HTTP 访问、首个账号创建与重复安装。该实机测试需要 Linux root 测试运行器来降权；它会在结束后移除自身的容器与卷。若要同时在一次性的 UID 1000 安装器容器中验证真实 sudo，请用 `--build-arg LOOPFORGE_TEST_BASE=your-image` 构建 `scripts/testdata/install-sudo.Dockerfile`，然后把该测试镜像作为 `LOOPFORGE_INSTALL_SUDO_TEST_IMAGE` 传入。生产安装器本身不需要 root。

在安装好 `e2e/` 依赖与 Chromium 后，从仓库根目录运行 `bash scripts/test-container.sh`。它会构建生产镜像，在 8093/33317 端口上创建隔离的 Compose 项目与数据库，创建测试账号，显式应用可观测性基线与公共目录，检查内置 CLI 与跨平台执行机器/门禁二进制，并运行公共浏览器套件。其容器与卷会在结束后被移除。若这些端口已被占用，请覆盖 `LOOPFORGE_CONTAINER_TEST_PORT` 与 `LOOPFORGE_CONTAINER_MYSQL_PORT`。该全新安装检查中模型调用是禁用的。

## Runner 本机登录与自动续期

对话工作区与 SOP 的 native、Docker 沙箱共用同一套登录准备逻辑。
API Key 模式沿用个人设置，不经过本机 OAuth 刷新管理器。

### Codex / Claude Code

Runner 保管宿主机原凭证。任务只能得到当前 access token 与本次任务的刷新能力，
不会得到上游 refresh token。任务在自己的 HOME 里换号、伪造身份字段或替换 refresh token，
cleanup 都不会把这些文件写回宿主机。

- **Codex**：私有 `auth.json` 中的 refresh token 是随机任务句柄，
  `CODEX_REFRESH_TOKEN_URL_OVERRIDE` 指向 Runner 的临时入口。官方 CLI 自己判断何时需要刷新，
  Runner 用宿主原凭证向 OAuth 服务申请，保存成功后返回 access token 和下一个临时句柄。
  同一旧句柄的重试复用原响应，不会再次刷新上游。
- **Claude Code**：通过 stream-json 的 `oauth_token_refresh` 控制通道回调 Runner，
  stdin 返回 access token。任务 credential 文件不含 refresh token；临近过期的宿主凭证在启动前续期。
  单次 SOP 收到最终结果后关闭输入；对话保留原有可继续发送消息的输入通道。

普通 Docker SOP 使用 `AGENTFLOW_DOCKER_NETWORK` 指定的网络。对话工作区和包含 Codex 账号登录节点的
Docker SOP 使用中继网络配置连接执行机器上的回调。SOP 的准备脚本、终端和执行节点共享同一个容器。

Claude Code 的回调在 **2.1.326** 的官方客户端中实测可用，但属于受入口限制的内部协议，
并不是公开稳定的 SDK 类型契约。当前绑定 `local-agent` 入口，内置安装版本为 2.1.326。
已知较旧版本或初始化失败会提示更新，不会退回向沙箱发送真实 refresh token。
未使用真实 Claude 订阅验收；测试使用官方二进制、虚构凭证与本机模拟认证/模型服务。

### 并发、持久化与账户切换

同一凭证来源使用进程内锁与跨进程文件锁。两个 SOP 同时刷新时，第一个完成上游交换，
后续请求复用宿主已经更新的凭证。已接入同一管理器的宿主进程也遵守这把锁。

刷新前记录交换状态，收到响应后先将完整新凭证保存到私有 journal，再原子替换宿主文件并同步磁盘。
最终只保留不含 token 的 hash receipt，供另一 Runner 进程识别该更新；正常完成后删除 journal。
进程重启时先恢复已收到的新凭证，避免重复使用已经轮换的旧 refresh token。
任务取消不取消已经开始的交换，最多等待独立的 30 秒期限来保存结果。

若请求已发出，但响应丢失或不可解析，旧 access token 和宿主文件保留；
同一份 refresh token 不会被自动重复兑换。此时需宿主登录源被重新登录或其他官方进程更新后才能继续续期。
客户端无法恢复从未收到的新 token。明确的 HTTP 4xx 拒绝（408 除外）允许以后重试。

宿主退出登录不会被 journal 复活；宿主切换账号时，已有任务不会接入新账号。
凭证来源为符号链接时，同时核对原路径；链接被删除或改指向后，停止使用旧目标，刷新中也不会向旧目标写回。
Codex 的用户身份与工作区共同作锚点；Claude 使用可信宿主 `.claude.json` 的账号/组织资料。
缺少账号资料时，只接受管理器自己有 receipt 的更新，其他变化需要重启任务。

默认私有状态目录为系统用户缓存目录下 `LoopForge/runner-auth`；可以用
`AGENTFLOW_RUNNER_AUTH_DIR` 指定持久目录，必须放在任务工作区之外。目录权限 `0700`，文件 `0600`。
native 托管任务遮蔽原凭证与刷新目录；Docker 只得到工作区中的私有副本。
任务结束会关闭刷新入口并移除临时凭证，不把刷新控制消息写入任务日志。

**独立启动、没有接入管理器的宿主机官方 CLI 不受这把锁约束。**
Runner 会尽量识别并保留宿主更新，文件内容复核不能等价于所有应用共同参与的事务。

### Antigravity

保持官方 CLI 在沙箱私有文件中自行刷新。当前 Google 登录实测允许并发重用同一 refresh token，
正常刷新会改变 access token，refresh token 不变。

cleanup 要求 refresh token 与宿主原件一致，并通过 Google OIDC userinfo 核验新 access token
属于原账号。access token 未变化时跳过写回。写回前检查 expiry 是尚未到期的时间戳，
显式提供的 token type 必须为 Bearer。保留宿主原有的账户资料及 refresh token。
宿主已变化、核验失败或只替换 refresh token 时继续保留宿主记录。
这没有实现 access-only 的长任务热更新，也没有把未来可能出现的 Google refresh-token 轮换当作已验证行为。

### 验证方式

普通测试不读取本机真实登录。可显式启用以下测试：

```sh

LOOPFORGE_PROBE_CODEX_BIN=/absolute/path/to/codex \
LOOPFORGE_PROBE_CLAUDE_BIN=/absolute/path/to/claude \
go test ./internal/runtime -run 'TestManagedLoginOfficial' -race -count=1

# 实际 native + Docker，对话和 SOP；使用 Python CLI 夹具与虚构 token
# 需要预先提供 python:3.13-alpine，macOS 的工作区放在 Docker 已共享的用户缓存目录
LOOPFORGE_PROBE_AUTH_SANDBOXES=1 \
go test ./internal/runtime -run TestManagedLoginRuntimePaths -race -count=1
```

Antigravity 的真实 Google 刷新实验单独 opt-in，命令及边界见
[验证记录](12-设计提案归档.md)。不与虚构认证代理共用进程。
